1. What Is Azure AI Search?

Azure AI Search (formerly Azure Cognitive Search) is a fully managed, cloud-hosted information retrieval service that connects enterprise data to AI. It unifies full-text, vector, hybrid, and multimodal query capabilities so apps, chatbots, and agents can ground answers in your proprietary content.

Two engines

  • Classic search — index-first, single request/response retrieval. You define an index, populate it, then query it directly. Low-latency, predictable, no LLM involved in retrieval itself.
  • Agentic retrieval — a multi-query pipeline where an LLM plans, decomposes, and iterates on a user's question, issuing several parallel sub-queries against one or more knowledge sources, then returns a structured, citation-rich response. This underpins Foundry IQ, the managed knowledge layer for agents in the Microsoft Foundry portal.

Core capabilities included with every search service

  • Full-text (keyword/BM25), vector, hybrid, and multimodal queries over indexed or remote content.
  • AI enrichment to chunk, vectorize, and otherwise transform raw content into searchable form.
  • Relevance tuning: scoring profiles, semantic ranker, filters, facets, synonyms, autocomplete.
  • Enterprise security (Microsoft Entra ID, Private Link, document-level RBAC) and Azure-scale monitoring.
  • Native integrations with Azure Blob Storage, Azure SQL, Cosmos DB, SharePoint, OneLake, Azure OpenAI, and Microsoft Foundry.

Two primary classic-search workloads

WorkloadDescription
IndexingLoads content into an index. Text is tokenized into inverted indexes; vectors go into vector indexes. Azure AI Search can only index JSON documents — non-JSON source content (PDFs, images) must be cracked/converted first.
QueryingA client app sends full-text, vector, hybrid, or multimodal query requests to a populated index and receives ranked results.
Must know: Azure AI Search indexes only JSON documents internally — an indexer or custom code must convert/crack source files (blobs, DB rows, images) into JSON before they can be indexed.

2. Ingesting & Indexing Content

There are exactly two ways to load data into a search index:

MethodAlso calledWhen to use
Push APIPush modelYou control serialization and push JSON documents directly via REST/SDK (Documents - Index API). Required for <5 min freshness, data not in a supported data source, or full control over timing/transformation logic.
IndexersPull modelA crawler ("indexer") connects to a supported data source, extracts ("cracks") content, maps fields, and populates the index automatically — no custom upload code. Runs on-demand or on a schedule (as frequent as every 5 minutes).

Indexer architecture

  • An indexer configuration = one data source + one index (+ optional skillset for enrichment).
  • An indexer can only read from one data source and write to one index, but a data source can feed multiple indexers, and multiple indexers can write into the same index (e.g., multi-source scenarios, multi-region sync, parallel indexing of huge datasets).
  • Supported data sources include Azure Blob Storage, Azure Data Lake Storage Gen2, Azure SQL Database/Managed Instance, Azure Cosmos DB (multiple APIs), Azure Table Storage, Microsoft OneLake, and SharePoint Online.
  • A search service runs one indexer job per search unit (replica) — add replicas for concurrent indexer execution; indexers don't run in the background, so heavy indexing can cause query throttling.

Document cracking

During indexing, the indexer "cracks" each source document — opening files and extracting text and images from formats such as PDF, Office docs, HTML, JSON, CSV — so content can be enriched and tokenized. Cracked images can be routed to image-processing skills (OCR, image analysis); cracked text is queued for NLP skills.

Content types for ingestion

  • Documents (PDF, Office, HTML, plain text) — cracked for text and embedded images.
  • Images — processed with OCR skill (printed/handwritten text) and Image Analysis skill (captions, tags) or multimodal embeddings.
  • Audio/video — not natively cracked by indexers; typically pre-processed outside Azure AI Search (e.g., Azure AI Speech for transcription, Azure Video Indexer) and the resulting transcript/metadata text is then pushed or indexed as JSON.
Tip: Indexer execution on Standard S3 HD and Serverless tiers follows a different model with a service-level daily runtime quota — know this exists even if details aren't required.
Must know: Push API = lowest latency / most control, you write the code. Indexers = no-code pull model with built-in change detection and scheduling, and they are the only way to drive a skillset/AI enrichment pipeline.

3. Index Schema Basics

An index is defined by a schema: a named collection of fields, each with a data type and a set of attributes controlling how it can be used in queries. A document in an index is conceptually like a row in a database table; the index itself is like a table.

Field attributes

AttributeMeaning
keyUnique document identifier (exactly one per index, must be a string).
searchableIncluded in full-text search (tokenized/analyzed). Only string and vector-adjacent text fields can be searchable.
filterableCan be used in $filter expressions (e.g., equality, range, geo-distance).
sortableCan be used in $orderby clauses.
facetableCan be used to generate facet navigation (counts/buckets of field values).
retrievableReturned in the select result set. Set to false to hide a field used only internally (e.g., a raw vector you never display).

Vector fields

  • Declared as Collection(Edm.Single) (or newer compressed/narrow types) with a required dimensions count and a vectorSearchProfile referencing an algorithm + vectorizer configuration.
  • Vector fields are not filterable directly, but you can pair them with a filterable text/numeric metadata field for "filtered vector search."
  • Only vector fields marked searchable (or specified in query searchFields) actually participate in vector search and scoring.

Scoring profiles

Optional, named boosting configurations attached to the index that let you weight certain fields (e.g., boost matches in Title over Body) or boost by freshness/distance/custom functions — applied to the text-relevance (BM25) portion of a query, not vectors.

Must know: a vector field can never be filterable itself — to filter vector search results you need a separate filterable scalar field in the same document (exam loves this trap).

Worked example: index schema with a vector field

REST body for PUT /indexes/docs-index?api-version=2026-04-01 — a minimal hybrid-ready index combining text and vector fields, plus the vectorSearch config block that the vector field's vectorSearchProfile points to:

JSON 
{
  "name": "docs-index",
  "fields": [
    { "name": "chunk_id", "type": "Edm.String", "key": true },
    { "name": "title",    "type": "Edm.String", "searchable": true, "filterable": true },
    { "name": "content",  "type": "Edm.String", "searchable": true },
    { "name": "page",     "type": "Edm.Int32",  "filterable": true, "sortable": true },
    {
      "name": "contentVector",
      "type": "Collection(Edm.Single)",
      "dimensions": 1536,
      "searchable": true,
      "retrievable": false,
      "vectorSearchProfile": "vector-profile"
    }
  ],
  "vectorSearch": {
    "algorithms": [
      { "name": "hnsw-alg", "kind": "hnsw", "hnswParameters": { "m": 4, "efConstruction": 400, "metric": "cosine" } }
    ],
    "profiles": [
      { "name": "vector-profile", "algorithm": "hnsw-alg" }
    ]
  }
}
Scenario: An architect notices the contentVector field above is set "retrievable": false. A teammate asks why a 1536-dimension field was indexed at all if it can't be returned. Answer: vector fields participate in similarity scoring but their raw numbers are useless to end users — you mark them retrievable:false to shrink the response payload, while a paired text field (e.g. content) is returned as the human-readable proxy for what matched.

4. Vector Search

Vector search indexes and queries over numeric embeddings instead of plain text, enabling matches based on semantic/conceptual similarity rather than exact keyword overlap — e.g., "dog" ≈ "canine", or "dog" (English) ≈ "hund" (German), or text ≈ an image of the same concept (multimodal).

Supported scenarios

  • Similarity search — encode text with an embedding model (e.g., Azure OpenAI text-embedding-ada-002 or newer, or open-source SBERT) and query with another embedding.
  • Hybrid search — vector + keyword search in one request (see Section 5).
  • Multimodal search — encode text and images into a shared embedding space (e.g., OpenAI CLIP, Azure AI Vision multimodal embeddings).
  • Multilingual search — embeddings naturally match concepts across languages with no translation step.
  • Filtered vector search — combine a vector query with a filter on a scalar field (applied pre- or post-vector search).
  • Vector database use — Azure AI Search can act as a pure vector store/long-term memory/knowledge base for RAG apps.

Getting embeddings into the index

ApproachHow it works
Integrated vectorization (internal)An indexer pipeline with a skillset calls an embedding model (e.g., Azure OpenAI Embedding skill) automatically during indexing, and a matching vectorizer encodes the query text at query time. Requires an indexer + data source + skillset.
External/bring-your-own vectorsYou generate embeddings yourself (any embedding model) and push pre-vectorized JSON documents directly into vector fields via the push API.

Algorithms (how matches are found)

AlgorithmTypeCharacteristics
Exhaustive KNNBrute-force, exactCompares the query vector against every vector (k-Nearest Neighbors), guaranteeing the true top-k. Expensive at scale; good for small/medium datasets, high-precision needs, or building ground truth to measure ANN recall. Doesn't consume vector index size quota.
HNSW (Hierarchical Navigable Small World)Approximate Nearest Neighbor (ANN)Builds a hierarchical graph at index time for fast, high-recall, low-latency search. Requires all vectors resident in memory (consumes vector index quota). Default/recommended for most production workloads.

Similarity metrics

  • Cosine — measures the angle between vectors (most common for text embeddings).
  • Dot product — fast, works well when vectors are normalized.
  • Euclidean — straight-line distance between vectors.
Tip: A query can set "exhaustive": true per vector query to force exhaustive KNN even if the field was indexed with HNSW — useful when you need maximum recall for a specific query without rebuilding the index.
Must know: HNSW = fast approximate search, consumes memory/vector quota; Exhaustive KNN = exact but computationally expensive, no quota consumption. Know when the exam wants "best recall at scale" (HNSW) vs. "guaranteed exact top-k" (exhaustive KNN).

Worked example: single-vector query (REST)

REST 
POST https://<service>.search.windows.net/indexes/docs-index/docs/search?api-version=2026-04-01
Content-Type: application/json
api-key: <admin-api-key>

{
  "vectorQueries": [
    {
      "vector": [0.0123, -0.0456, 0.0789, "... 1536 floats total"],
      "fields": "contentVector",
      "kind": "vector",
      "k": 10,
      "exhaustive": false
    }
  ],
  "select": "title, content, page",
  "top": 10
}
Scenario: A support-ticket search index holds 40M vectors and must answer queries in under 100ms at production scale, but a nightly batch job must also verify ANN recall against a perfectly accurate baseline. Answer: use the HNSW algorithm (default, in-memory graph) for the live production queries, and issue the batch-verification queries with "exhaustive": true on the vector query — this forces exact KNN for that one request without re-indexing or changing the field's configured algorithm.

5. Hybrid Search

Hybrid search is a single query request that runs full-text (keyword/BM25) search and vector search in parallel against the same index, then merges the two ranked result sets into one unified list using Reciprocal Rank Fusion (RRF).

Why combine them?

  • Vector search strength: finds conceptually similar content even with zero keyword overlap.
  • Keyword search strength: precision for exact matches — product codes, jargon, dates, names — cases where embeddings can blur exact terms.
  • Benchmarks show hybrid retrieval plus semantic ranker gives the best relevance for RAG grounding data.

Request anatomy

  • search — the full-text query string.
  • vectorQueries — one or more vector queries, each targeting a vector field, with a k (nearest neighbors to retrieve) and optional exhaustive/oversampling.
  • filter, facets, select — standard text-query features that still apply in hybrid mode.
  • queryType: "semantic" + semanticConfiguration — optionally layer semantic ranker on top (recommended: set vector k to 50 to maximize semantic ranker's input).
Tip: Both full-text and vector queries run against the same index — a hybrid-capable index simply contains both plain-text/numeric fields and vector fields side by side.
Must know: Hybrid search ranking = RRF (Reciprocal Rank Fusion), not a weighted average of scores. RRF merges rankings from BM25 (text) and HNSW/eKNN (vector) without needing the two different score scales to be comparable.

Worked example: hybrid query (REST and Python)

REST 
POST https://<service>.search.windows.net/indexes/docs-index/docs/search?api-version=2026-04-01
Content-Type: application/json
api-key: <admin-api-key>

{
  "search": "historic hotel walk to restaurants and shopping",
  "vectorQueries": [
    {
      "vector": [-0.00915, 0.01871, "... remaining floats"],
      "fields": "contentVector",
      "kind": "vector",
      "k": 50,
      "exhaustive": false
    }
  ],
  "queryType": "semantic",
  "semanticConfiguration": "default-semantic-config",
  "select": "title, content, page",
  "top": 10
}
Python 
from azure.identity import DefaultAzureCredential
from azure.search.documents import SearchClient
from azure.search.documents.models import VectorizedQuery

client = SearchClient(endpoint=endpoint, index_name="docs-index",
                       credential=DefaultAzureCredential())

vector_query = VectorizedQuery(vector=query_vector, k_nearest_neighbors=50,
                                fields="contentVector")

results = client.search(
    search_text="historic hotel walk to restaurants and shopping",  # BM25 leg
    vector_queries=[vector_query],                                   # vector leg
    query_type="semantic",
    semantic_configuration_name="default-semantic-config",
    select=["title", "content", "page"],
    top=10,
)
for r in results:
    print(r["title"], r["@search.reranker_score"])
Scenario: A product-catalog search must match an exact SKU like SKU-48213 typed by a warehouse worker, but also surface conceptually similar items when a shopper types "comfortable running shoes for flat feet." Answer: this is a textbook case for hybrid search, not pure vector search — the keyword/BM25 leg nails the exact SKU token match that an embedding could blur, while the vector leg captures the semantic "comfortable running shoes" intent; RRF merges both into one ranked list.
Scenario: Query latency and relevance are both acceptable with hybrid search alone, but stakeholders want extractive answer snippets and better handling of natural-language questions ("What's the cancellation policy?"). Answer: add the semantic ranker on top of the existing hybrid query (queryType: "semantic" + a semanticConfiguration) rather than re-architecting retrieval — it reranks the top 50 hybrid results and can return semantic captions/answers, which is exactly the missing capability.

6. Semantic Ranker

Semantic ranker is a premium, billed (with a free-tier allowance) query-time feature that reranks an initial BM25- or RRF-ranked result set using Microsoft's language-understanding (deep learning) models adapted from Bing — improving relevance for text, the text portion of vector queries, and hybrid queries.

What it adds to the pipeline

CapabilityDescription
L2 (secondary) rankingRescoring the top results (max 50) using semantic/contextual meaning, not just term frequency.
Semantic captions & highlightsExtracts verbatim summarizing sentences/phrases per result and highlights key passages.
Semantic answersOptional direct "answer" extracted from a result when the query looks like a question and a document contains answer-like text.
Query rewrite (preview)Generates up to 10 semantically similar query variants (typo correction, rephrasing/synonyms) that are run and merged before reranking.

How it works

  1. Start from a BM25-ranked (text) or RRF-ranked (hybrid/vector) result.
  2. Summarize/truncate the top 50 results for the ranking model (resource and latency constraints mean only the top 50 progress, even if more results exist).
  3. Score with the semantic model and return rescored results + optional captions/answers.
Tip: Semantic ranker is also built into agentic retrieval by default — you don't configure it separately in that pipeline.
Must know: Semantic ranker only reranks the top 50 results from the prior BM25/RRF pass — it is a reranking layer, not a replacement retrieval engine, and it requires text content (it can't rerank on raw vectors alone).

7. AI Enrichment / Skillsets (Cognitive Skills)

AI enrichment integrates Azure AI (Foundry Tools/Cognitive Services) into the indexer pipeline to process content that isn't natively searchable — turning raw text/images into structured, searchable (and vectorized) fields. Raw input to enrichment must be text or images (you cannot enrich vectors).

Pipeline components

  • Skillset — a named, ordered collection of skills attached to an indexer, each performing one atomic transformation.
  • Built-in skills — call Foundry Tools/Cognitive Services APIs under the hood:
    • OCR — extract printed/handwritten text from images/scanned documents.
    • Image Analysis — generate captions/tags/descriptions for images as searchable text.
    • Entity Recognition — extract people, places, organizations from text.
    • Key Phrase Extraction — identify important terms.
    • Language detection & Translation — for multilingual content.
    • Text Split skill — chunk long text into smaller passages (critical for RAG/embedding size limits).
    • Azure OpenAI Embedding skill — generate text embeddings for integrated vectorization.
    • Azure AI Vision multimodal embedding skill — generate shared text/image embeddings.
  • Custom skills — call your own external code (typically an Azure Function or any HTTP endpoint implementing the custom skill interface) for processing not covered by built-in skills.

Enrichment pipeline flow

  1. Import — indexer connects to a data source (commonly Azure Blob Storage) and pulls raw content.
  2. Enrich & Index — the indexer cracks documents (extracts text/images), skills process content into an enriched document (an internal "enrichment tree" collecting each transformation), then field mappings (source → index) and output field mappings (enriched content → index) route data into the index. Lexical analysis/tokenization happens during this indexing step.
  3. Explore — output is always a search index; optionally also a knowledge store (tables/blobs in Azure Storage for downstream analytics/BI, defined via projections) — the same enriched content can flow to both simultaneously.
Tip: Enable the enrichment cache (preview) to persist skill outputs so that re-running a skillset after a schema tweak doesn't require (and re-bill) every skill from scratch — only changed skills rerun.
Must know: Custom skills plug into a skillset as an external HTTP call — the canonical AI-103 example is wrapping custom logic in an Azure Function that conforms to the custom skill request/response JSON contract.

Worked example: chained skillset (OCR → Text Split → Embedding)

A skillset is a top-level resource (PUT /skillsets/my-skillset) with a skills array. Each skill declares its context (where it runs) and inputs/outputs that wire it to the enrichment tree — the output of OCR becomes input to Text Split, whose output chunks become input to the Embedding skill:

JSON 
{
  "name": "chunk-embed-skillset",
  "skills": [
    {
      "@odata.type": "#Microsoft.Skills.Vision.OcrSkill",
      "context": "/document/normalized_images/*",
      "inputs": [ { "name": "image", "source": "/document/normalized_images/*" } ],
      "outputs": [ { "name": "text", "targetName": "ocrText" } ]
    },
    {
      "@odata.type": "#Microsoft.Skills.Text.SplitSkill",
      "context": "/document",
      "textSplitMode": "pages",
      "maximumPageLength": 2000,
      "pageOverlapLength": 200,
      "inputs": [ { "name": "text", "source": "/document/content" } ],
      "outputs": [ { "name": "textItems", "targetName": "chunks" } ]
    },
    {
      "@odata.type": "#Microsoft.Skills.Text.AzureOpenAIEmbeddingSkill",
      "context": "/document/chunks/*",
      "resourceUri": "https://<your-aoai>.openai.azure.com",
      "deploymentId": "text-embedding-3-small",
      "modelName": "text-embedding-3-small",
      "inputs": [ { "name": "text", "source": "/document/chunks/*" } ],
      "outputs": [ { "name": "embedding", "targetName": "chunkVector" } ]
    }
  ],
  "cognitiveServices": {
    "@odata.type": "#Microsoft.Azure.Search.CognitiveServicesByKey",
    "key": "<foundry-resource-key>"
  }
}
Tip: Notice the context escalates from /document/normalized_images/* (once per image) to /document (once per document) to /document/chunks/* (once per chunk) — the embedding skill must run per-chunk so each chunk gets its own vector, not one vector for the whole document.

8. Configuring a RAG Ingestion Flow

Retrieval-Augmented Generation (RAG) grounds an LLM's response in your proprietary content instead of relying solely on its training data. Azure AI Search offers two complementary approaches:

ApproachDescription
Classic RAG patternYou build the pipeline: hybrid search + semantic ranking retrieves the best chunks, your app (or Azure OpenAI "on your data" / Foundry) assembles a prompt with those chunks and calls the LLM. Proven, GA, millisecond query times, full control.
Agentic retrievalA complete, LLM-orchestrated RAG pipeline: query planning (decomposing a conversational question into targeted sub-queries), parallel multi-source retrieval across knowledge sources (indexed or remote, e.g. SharePoint/Bing), built-in semantic ranking, and a structured response with citations — purpose-built for agent consumption via knowledge bases.

End-to-end ingestion flow (classic RAG, including OCR)

  1. Data source — point an indexer at Blob Storage/SharePoint/OneLake/etc. holding source documents (PDFs, scanned images, Office files).
  2. Document cracking — indexer extracts text and embedded images from each file.
  3. OCR skill — run on image content (scanned pages, photos of documents) to extract text that isn't otherwise machine-readable.
  4. Text Split skill (chunking) — break long text into overlapping chunks sized to fit embedding-model and LLM context limits (common strategies: fixed token/character count with overlap, or page/sentence-aware splitting). Chunking quality directly drives retrieval relevance and RAG answer quality.
  5. Embedding skill — call an embedding model (Azure OpenAI/Azure AI Foundry embeddings, or Azure AI Vision for images) over each chunk to generate vectors — this is integrated vectorization.
  6. Index — enriched chunks (text + vector + metadata like source file, page number) are written to a search index with hybrid-ready fields.
  7. Query & ground — at query time, run a hybrid (+ semantic ranker) query to retrieve the top relevant chunks, then pass them as grounding context into the LLM prompt (Azure OpenAI chat completion or a Foundry agent).

Challenges RAG must solve, and how Azure AI Search addresses them

ChallengeClassic RAG mitigationAgentic retrieval mitigation
Query/intent understandingHybrid search + semantic ranking match concepts, not just keywords.LLM decomposes vague/conversational queries into focused sub-queries using conversation history.
Multi-source dataIndexers pull from 10+ Azure data sources into one index.Knowledge bases unify multiple knowledge sources; can query SharePoint/Bing remotely without pre-indexing.
Token constraintsSemantic ranking + top-k/top-n limits + scoring profiles + select trims payload.Returns only most-relevant chunks with citation tracking; optional answer synthesis.
Response timeMillisecond single-request latency.Parallel sub-query execution; adjustable reasoning effort (minimal/low/medium).
Security/governanceDocument-level access control, Entra ID, RBAC.Same, plus permission-aware knowledge bases (Foundry IQ).
Tip: Chunking strategy and chunk size are an exam-relevant design decision — too large and you waste LLM tokens/dilute relevance; too small and you lose context needed for a coherent answer. The Text Split skill supports configurable page length and overlap.
Must know: The canonical RAG ingestion chain for scanned/image-based documents is: indexer → document cracking → OCR skill → Text Split (chunking) skill → embedding skill (integrated vectorization) → index. Expect a scenario question asking you to order or pick the missing skill in this chain.

9. Connecting Retrieval Pipelines to Agents (Grounding/Tool Source)

Azure AI Search underpins Foundry IQ, the managed knowledge layer that turns enterprise content into reusable, permission-aware knowledge for agents built in the Microsoft Foundry portal (and via Foundry Agent Service).

Key building blocks

  • Knowledge source — a pointer to retrievable content. Can be an indexed knowledge source (a search index containing vector/text fields plus a vectorizer) or a remote source (SharePoint, Bing) queried directly without pre-indexing.
  • Knowledge base — one or more knowledge sources grouped together with retrieval instructions that guide the LLM on which sources to use and how.
  • Connecting to Foundry Agent Service — you parent a knowledge source to a knowledge base, then connect that knowledge base to the agent so it can call retrieval as a tool during its reasoning loop, receiving structured, cited results it can use for grounded responses.

Why this matters for app/agent builders

  • Agents built in Microsoft Foundry (or via the Azure AI Foundry SDK) can treat Azure AI Search as a first-class retrieval tool, no custom query-orchestration code required — the agentic retrieval engine handles query planning and parallel execution.
  • For simpler scenarios (or where GA features are required instead of preview), you wire classic hybrid + semantic queries yourself into your agent's tool-calling logic or RAG prompt assembly (e.g., Azure OpenAI "on your data," LangChain/Semantic Kernel vector store integrations, or a custom tool/function in a Foundry agent).
  • Either way, the index is the grounding "source of truth" — citations in the agent's final answer trace back to specific indexed/retrieved documents and chunks.
Must know: The Foundry integration chain is index (with vectorizer) → knowledge source → knowledge base → Foundry Agent Service. The exam may ask which object you "parent" to which — knowledge sources are parented to knowledge bases, and knowledge bases connect to the agent.
Scenario: A team already has a populated Azure AI Search index (text + vector fields, vectorizer configured) and wants a Foundry agent to answer employee questions by searching it, with minimal custom orchestration code. Answer: wrap the index as an indexed knowledge source, add it to a knowledge base with retrieval instructions, then connect that knowledge base to the agent in Foundry Agent Service — the agent calls agentic retrieval as a tool and gets back structured, cited results, with no hand-written query-planning code required.

10. Hands-On Patterns — Full RAG Ingestion-to-Grounding Pipeline

Putting Sections 2–9 together into one concrete, end-to-end flow you could be asked to sequence on the exam:

  1. Chunk — Text Split skill breaks each cracked document into overlapping passages (e.g. maximumPageLength: 2000, pageOverlapLength: 200) sized for the embedding model's input limit.
  2. Embed — Azure OpenAI Embedding skill (or external/bring-your-own embeddings via the push API) converts each chunk into a Collection(Edm.Single) vector — this is integrated vectorization.
  3. Index — indexer writes each chunk + vector + metadata (source file, page, title) into a hybrid-ready index with an hnsw vector profile.
  4. Query — at request time, issue one hybrid query: search (BM25 text) + vectorQueries (ANN/HNSW) merged via RRF, optionally reranked with queryType: "semantic".
  5. Ground the LLM — take the top-n returned chunks (after select trims to human-readable fields) and inject them into the LLM prompt (Azure OpenAI chat completion or a Foundry agent's tool-call result), so the model answers using your content with traceable citations back to title/page.
Python 
# Step 4+5 combined: retrieve, then ground an LLM call
results = search_client.search(
    search_text=user_question,
    vector_queries=[VectorizedQuery(vector=embed(user_question),
                                     k_nearest_neighbors=50, fields="contentVector")],
    query_type="semantic", semantic_configuration_name="default-semantic-config",
    select=["title", "content", "page"], top=5,
)
context = "\n\n".join(f"[{r['title']} p.{r['page']}] {r['content']}" for r in results)
prompt = f"Answer using ONLY the context below. Cite [title p.N].\n\n{context}\n\nQ: {user_question}"
response = openai_client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": prompt}],
)
Must know: this chain — chunk → embed → index → hybrid+semantic query → ground — is the exam's reference RAG pipeline. Questions often give you a broken/partial pipeline (e.g., missing Text Split skill, or a vector-only query with no semantic ranker) and ask what's missing or misordered.

11. Templates & Best Practices

Production-grade checklist and reusable templates for index design, chunking, relevance tuning, security, and capacity — the areas most "which configuration should you choose" exam questions probe.

11.1 Index design — selective field attribution

The single most common index-design mistake: marking every field as searchable, filterable, sortable, and facetable "just in case."

  • Only set the attributes you actually query. Each attribute adds a separate storage structure — filterable/sortable store raw non-analyzed copies; facetable builds a value list; searchable builds the inverted index.
  • Over-attribution can quadruple storage and slow both indexing and query scanning, since every searchable field is scanned on a full-text query.
  • A field that is facetable + filterable + searchable simultaneously is capped at 16 KB of text; a plain searchable field can hold up to 16 MB.
  • Periodically revisit schema + document size as the index grows — smaller indexes query faster because more of them stays cached in memory.
JSON 
{
  "name": "docs-index",
  "fields": [
    { "name": "id", "type": "Edm.String", "key": true },
    { "name": "title", "type": "Edm.String", "searchable": true, "sortable": true },
    { "name": "content", "type": "Edm.String", "searchable": true },
    { "name": "contentVector", "type": "Collection(Edm.Single)", "dimensions": 1536,
      "vectorSearchProfile": "vector-profile", "searchable": true, "retrievable": false },
    { "name": "category", "type": "Edm.String", "filterable": true, "facetable": true },
    { "name": "publishedDate", "type": "Edm.DateTimeOffset", "filterable": true, "sortable": true }
    // NOT filterable/facetable/sortable: "content" — it's long free text, never filtered on
  ]
}
Scenario: An index has grown slow on both indexing and query latency. Review shows every field — including a 10,000-character "content" field — is marked searchable, filterable, facetable, and sortable.
Answer: Remove filterable/facetable/sortable from the long free-text field (keep only searchable), since those attributes were never queried for that field; this directly cuts storage and scan cost without losing functionality.

11.2 Chunking strategy template

Chunking exists to stay under model input token limits (e.g., text-embedding-3-small caps at 8,191 tokens / ~6,000 words) and to avoid diluting a single vector with too many unrelated topics.

TechniqueWhen to useBuilt-in tool
Fixed-size chunksGeneral-purpose default; predictable size for embeddingsText Split skill (pageLength/maximumPageLength)
Variable-size (sentence/markup aware)HTML/Markdown with real heading structureContent Understanding skill, or Text Split "sentences" mode
Semantic chunksPreserve meaning across paragraph/page boundariesContent Understanding skill (semantic chunking, markdown output)
Document parsing (one-to-many)Source naturally splits into sub-documents (e.g. book → chapters)One-to-many indexing / Markdown-blob indexing
Starting-point rule of thumb (memorize for the exam): chunk size ≈512 tokens (~2,000 characters) with ~25% overlap (~128 tokens) — large enough to preserve context, small enough to stay well under embedding/LLM input limits, with overlap preventing hard cuts mid-sentence from losing meaning at chunk boundaries.
JSON (skillset fragment) 
{
  "@odata.type": "#Microsoft.Skills.Text.SplitSkill",
  "textSplitMode": "pages",
  "maximumPageLength": 2000,
  "pageOverlapLength": 500,
  "unit": "characters",
  "inputs": [{ "name": "text", "source": "/document/content" }],
  "outputs": [{ "name": "textItems", "targetName": "chunks" }]
}
Scenario: Embeddings are being generated per-page for long legal contracts, and retrieval quality is poor because key clauses get split across adjacent pages with no shared context.
Answer: Add page overlap (e.g. 25% of chunk length) in the Text Split skill, or move to semantic/variable chunking that respects clause/section boundaries, instead of hard fixed-size splits with zero overlap.

11.3 Scoring profile template (relevance tuning)

Scoring profiles boost/suppress document ranking using your own business rules — they do not require an index rebuild and can be added/edited/deleted live.

  • Weighted text fields — matches in title count more than matches in body.
  • Freshness function — boosts more recent Edm.DateTimeOffset values.
  • Distance function — boosts documents closer to a supplied geo-point.
  • Magnitude/range function — boosts based on a numeric field falling in/near a target range (e.g. price, rating).
  • Tag function — boosts if any value in a string collection matches the query's tag list.
JSON 
{
  "name": "boost-recent-and-title",
  "text": { "weights": { "title": 3, "content": 1 } },
  "functions": [
    {
      "type": "freshness",
      "fieldName": "publishedDate",
      "boost": 5,
      "interpolation": "linear",
      "freshness": { "boostingDuration": "P90D" }
    }
  ],
  "functionAggregation": "sum"
}
Scenario: A news-search index must rank recently published articles higher, and matches found in the headline should count more than matches in the article body.
Answer: Create a scoring profile combining a text.weights boost on the title field with a freshness function on the publish-date field — no index rebuild required, and it can be applied selectively per query via scoringProfile=.

11.4 Security best practices

ControlRecommendation
AuthenticationPrefer Microsoft Entra ID / RBAC over API keys; disable local (key-based) auth once RBAC is verified working for all clients.
Built-in rolesSearch Service Contributor (manage the service/objects, no data read/write), Search Index Data Contributor (read/write documents), Search Index Data Reader (query/read documents only) — assign the narrowest role per principal/agent.
Network isolationUse a private endpoint (Azure Private Link) to remove public network exposure; combine with firewall IP rules for defense in depth during transition.
Document-level securityUse row-level / document-level access control (security filters or Microsoft Entra group-based filters) when different users must see different subsets of the same index.
TransportTLS 1.2/1.3 is enforced automatically by the service — no customer action required, but client code must support it.
Encryption at restAES-256 service-managed by default; add customer-managed keys (CMK) via Key Vault if compliance requires control over the encryption key.

Scenario: A Foundry agent only needs to run queries against an index; it must never be able to create, delete, or rebuild indexes.
Answer: Assign the agent's managed identity the Search Index Data Reader role scoped to the search service (not Search Service Contributor, which manages the service/schema but has no document data access by itself, and not Search Index Data Contributor, which also allows writes).

11.5 Capacity planning & performance

ModelHow it worksBest for
DedicatedPre-provision replicas (throughput/HA) × partitions (storage); billed hourly in Search Units regardless of usagePredictable, steady workloads
Serverless (preview)Auto-scales with demand, can scale to zero when idle; billed by Compute Units + storage actually usedBursty, variable, or multi-tenant/agent-driven workloads
  • Replicas increase query throughput and high availability (query/indexing load spread across replicas).
  • Partitions increase storage capacity and indexing throughput (data sharded across partitions).
  • Scale up (bigger tier, e.g. move to S2) vs. scale out (more replicas/partitions) is a classic trade-off: scale out first for query concurrency, scale up when a single index/document is simply too large or complex for the current tier's per-partition limits.
Must know: replicas = availability & query throughput; partitions = storage & indexing throughput. If an exam scenario describes slow query response under concurrent load, the fix is usually "add replicas"; if it describes running out of storage or slow bulk indexing, the fix is usually "add partitions."

11.6 Production RAG index checklist

  • ☐ Field attributes minimized to only what's queried (search/filter/sort/facet as needed, nothing extra)
  • ☐ Chunking: ~512 tokens / ~25% overlap starting point, tuned per content type
  • ☐ Vector field uses an appropriate HNSW profile with matching embedding model dimensions
  • ☐ Hybrid query (BM25 + vector via RRF) enabled, with semantic ranker layered on top for re-ranking
  • ☐ At least one scoring profile if business rules (freshness, authority, category) should influence ranking
  • ☐ Microsoft Entra ID / RBAC enabled; key-based auth disabled once verified; narrowest role assigned per caller
  • ☐ Private endpoint configured if the index holds non-public/internal content
  • ☐ Capacity model chosen deliberately: Dedicated for steady load, Serverless for bursty/agent-driven load

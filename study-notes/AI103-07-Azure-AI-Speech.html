1. Service Overview & Resources

Azure AI Speech (now branded as part of Azure AI Foundry "Foundry Tools") provides speech-to-text, text-to-speech, speech translation, and live voice-agent capabilities through an Azure AI Foundry / Cognitive Services Speech resource. It can run in the cloud or at the edge via containers, and is accessible from the Speech SDK, Speech CLI (spx), and REST APIs.

Common exam-relevant scenarios

  • Captioning — synchronized live/offline captions, profanity filtering, partial results, language identification for multilingual content.
  • Audio content creation — neural voices for chatbots/voice agents, e-books → audiobooks, in-car navigation.
  • Call center analytics — real-time or batch transcription of calls, PII redaction, sentiment/insight extraction.
  • Language learning — pronunciation assessment, real-time transcription, read-aloud materials.
  • Voice Live — natural, humanlike speech-to-speech conversational agent interfaces (see Section 6).
  • Speech translation — real-time speech-to-speech translation; translated video generation.
  • Video avatar creation — synthetic talking-avatar videos (real-time and batch).
Must know: Azure AI Speech is consumed through ONE Speech (or multi-service Azure AI Foundry) resource that exposes STT, TTS, translation, and voice capabilities together — you don't provision separate resources per feature.

2. Speech-to-Text (STT)

Speech to text converts audio into text. Azure offers three processing modes — know when to pick each for the exam:

ModeDescriptionBest for
Real-time transcriptionStreams audio and returns interim + final results instantly via SDK/CLI/REST (short audio)Live captioning, contact-center voice agents, agent-assist, voice assistants/chatbots
Fast transcriptionSynchronous transcription of an audio file; fastest turnaround with predictable latencyVideo editing, voicemail transcription, meeting notes, quick post-call analytics
Batch transcriptionAsynchronous processing of large volumes of stored audio via RESTPost-call QA/compliance, bulk subtitle/caption generation, training data pipelines

Continuous recognition

Real-time (continuous) recognition is event-driven: the SDK raises Recognizing (interim) and Recognized (final) events as audio streams in, instead of a single blocking call — essential for live/conversational scenarios and for agent architectures that need to react as the user speaks.

Key STT capabilities

  • Multichannel transcription — real time STT can transcribe up to two audio channels independently and tag each result with its source channel (e.g., two sides of a support call).
  • Diarization — distinguishes and labels up to 35 different speakers in one recording; useful for meetings/multi-speaker calls.
  • Phrase lists — supply domain-specific words/phrases (jargon, proper nouns) to bias recognition accuracy without full custom-model training.
  • Language identification (LID) — automatically detects the spoken language when it isn't known in advance, or across multilingual audio.

Model options (fast transcription endpoint)

ModelUse when you need…
Azure LLM SpeechFlagship LLM-powered model — best contextual/multilingual accuracy, custom prompting, built-in translate mode
Azure TranscribeGeneral-purpose default model with diarization, phrase lists, LID, timestamps
MAI-Transcribe-2Alternative model to evaluate for workload-specific accuracy/performance (check preview status)
For the exam, remember the simple decision rule: streaming/live input → real-time; single file, need result fast → fast transcription; large stored volumes, not time-sensitive → batch transcription.
Must know: Real-time STT is the correct choice for conversational/agentic interactions (voice assistants, contact-center agent assist) because it streams interim results; batch transcription is asynchronous and unsuitable for live conversation.

3. Text-to-Speech (TTS)

Text to speech (speech synthesis) converts text into humanlike audio using deep neural networks, reducing listening fatigue versus legacy concatenative synthesis.

Voice options

  • Standard (neural) voices — 100+ languages/locales, available out-of-the-box at 24 kHz and high-fidelity 48 kHz; browse the Voice Gallery in Speech Studio.
  • Custom voice — umbrella term for professional voice fine-tuning (brand voice from studio recordings) and personal voice (an individual's own voice, limited-access/responsible-use gated). Requires application/approval before use.
  • HD voices / Azure OpenAI voices — higher-quality options for more versatile or expressive scenarios.

SSML (Speech Synthesis Markup Language)

SSML is the XML-based language used to fine-tune TTS output. Candidates should recognize it can control:

  • Pitch, speaking rate, volume, and pauses
  • Pronunciation (phoneme tags) and custom lexicons
  • Speaking styles and multiple voices within one document
  • Multilingual voice switching (for multilingual neural voices)
Example SSML skeleton: <speak version="1.0" xml:lang="en-US"><voice name="en-US-AvaNeural">Hello, <break time="300ms"/> how can I help?</voice></speak>

Synthesis modes

  • Real-time speech synthesis — via Speech SDK/REST, for interactive apps (chat/voice agents).
  • Batch synthesis API — asynchronous synthesis for audio longer than 10 minutes (audiobooks, lectures); you poll for completion and download output rather than receiving it live.

Visemes

Visemes are the key mouth/lip/jaw poses corresponding to phonemes; the Speech SDK can emit viseme events to drive facial/avatar animation (currently richest support for en-US neural voices).

Custom Neural Voice (CNV) — concepts

  • Built from a handful of studio-quality audio samples + transcriptions.
  • Two flavors: professional voice fine-tuning (brand voices, gated access) and personal voice (per-user, usable with Live Interpreter for speech-to-speech translation in the user's own voice).
  • Training/hosting are billed separately: professional fine-tuning is measured in compute hours (typ. 20–40 hrs single-style, ~90 hrs multi-style, capped at 96 hrs); endpoint hosting billed hourly whenever the endpoint is active.
Must know: TTS billing counts every character sent in the SSML body (letters, numbers, spaces, punctuation, markup except <speak>/<voice> tags) — and each CJK character (Chinese/Japanese kanji/Korean hanja) counts as two characters for billing, even if no audio is produced due to a language mismatch.

4. Custom Speech

Custom speech lets you evaluate and improve speech-to-text accuracy for your domain. It can be applied to real-time STT, speech translation, and batch transcription.

Why/when to use it

  • The default Universal Language Model (base model, trained by Microsoft, updated periodically) handles most general scenarios well.
  • Use a custom model when the base model mis-recognizes domain-specific vocabulary (medical terms, product names, acronyms) or struggles with specific acoustic conditions (background noise, accents, microphone quality).
  • You can train with text data (to add vocabulary), audio + transcriptions (to adapt to acoustic conditions), structured text (patterned data), and define custom pronunciations, inverse text normalization, custom rewrite, and custom profanity filtering.
  • Use multiple custom models when a domain has multiple sub-areas, each with its own vocabulary (e.g., different Olympic sports).

Custom speech workflow (Speech Studio)

  1. Create a project and choose a base model.
  2. Upload test data to evaluate current accuracy.
  3. Train a model with transcripts/related text and audio.
  4. Inspect recognition quality by listening to test audio vs. transcription.
  5. Evaluate quantitatively using Word Error Rate (WER) — a high WER signals the need for more/better training data.
  6. Deploy the model to a custom endpoint (required for real-time/translation use; not required for batch transcription, which can reference the trained model directly).
You are billed for custom speech model usage and endpoint hosting, and (for base models created Oct 2023+) for training itself. If a custom model is only used for batch transcription, you can skip hosting a dedicated endpoint and save cost.
Must know: Custom Speech = improving accuracy/vocabulary recognition for STT (via WER-driven training), which is distinct from Custom Neural Voice = creating a unique synthesized voice for TTS. The exam loves to swap these two.

5. Speech Translation

Speech translation provides end-to-end, real-time, multi-language translation of spoken audio, returning translated text, synthesized speech, or both.

Two approaches

ApproachDescription
Standard speech translation APISend audio in a known source language; receive translated text and/or synthesized speech in a specified target language. One dedicated Speech Translation API.
Live InterpreterA richer, conversational mode of real-time translation: auto-detects the spoken language (no need to pre-set it), supports mid-conversation language switching, low-latency speech-to-speech output, and can use the speaker's own "bring your own" personal voice for natural-sounding translated output.
  • Supports multiple target languages from a single input stream in one request.
  • Live Interpreter use cases: personal interpretation (phones, earbuds, AI glasses), contact-center multilingual support, international meetings.

Dedicated API vs. transcribe-then-translate (LLM/Foundry pipeline)

For agentic/Foundry-based architectures there are two valid design patterns and the exam expects you to choose correctly:

  • Dedicated Speech Translation API / Live Interpreter — lowest latency, purpose-built for real-time speech-to-speech translation, ideal when translation is the primary scenario (e.g., live interpreter devices, multilingual contact centers).
  • Transcribe (STT) → translate with an LLM/text-translation step → optionally re-synthesize (TTS) — a composable pipeline useful when you need custom business logic, grounding, or combined reasoning (e.g., summarize + translate + answer) as part of a larger agent orchestration, at the cost of extra hops/latency versus the dedicated API.
  • Azure LLM Speech (fast transcription enhanced mode) also exposes a built-in translate operation that converts pre-recorded audio directly into text in a target language — a middle ground between the two approaches for file-based (not real-time streaming) workloads.
Must know: Choose the dedicated Speech Translation API / Live Interpreter for low-latency, real-time speech-to-speech translation; choose an STT-then-LLM-translate pipeline when the agent needs additional reasoning, grounding, or orchestration beyond simple translation.

6. Speech as an Agent Modality (Voice Live API)

The Voice Live API is Microsoft's managed solution for building voice-driven conversational agents — directly relevant to the AI-103 "agents" theme. Instead of manually chaining STT → LLM → TTS (which adds engineering complexity and perceived latency), Voice Live integrates speech recognition, generative AI reasoning, and text-to-speech into one unified, fully managed, low-latency interface.

How it works

  • Developers send audio input and receive audio output, optional avatar visuals, and action/function triggers.
  • No need to deploy or manage the underlying generative models yourself — fully managed backend.
  • Communication is via WebSocket events; API design is intentionally compatible with the Azure OpenAI Realtime API event shapes, so existing realtime-API client code is largely reusable.

Key agent-relevant features

  • Model choice: GPT-Realtime, GPT-5, GPT-4.1, GPT-4o, Phi, and more — trade off intelligence, latency, and cost; all fully managed (no capacity planning).
  • Function calling — lets the voice agent call external tools/APIs and ground responses (the "VoiceRAG" pattern: retrieval-augmented voice responses).
  • Conversational quality features: noise suppression, echo cancellation, robust interruption detection, advanced end-of-turn (turn-taking) detection for natural pauses.
  • Customization: phrase lists or custom speech models for input recognition; custom voice for branded output; avatar integration for a visual identity.
  • Broad locale coverage: 140+ locales for STT, 600+ standard voices across 150+ locales for TTS.

Multimodal reasoning from audio

Because Voice Live routes audio directly to a multimodal/generative model (rather than a hard STT→text→LLM boundary), the agent can reason over tone, pauses, and full acoustic context in addition to transcribed words — enabling more natural handling of interruptions and ambiguity than a traditional STT-then-text-LLM pipeline.

For scenarios where you still want full manual control (or need to combine with services Voice Live doesn't natively support), the classic composable pattern is still valid: real-time STT → your orchestration/LLM/agent logic → TTS output. Voice Live is the "fast path" that collapses this chain for most conversational voice-agent needs.
Must know: Voice Live API = the managed, end-to-end speech-to-speech agent service (STT + LLM + TTS + turn-taking, in one WebSocket API, Azure-OpenAI-Realtime-API compatible) — this is the exam's answer whenever a scenario calls for "build a low-latency conversational voice agent without orchestrating separate speech components."

7. Speaker Recognition

Documentation note: The dedicated "Speaker Recognition overview" page has been retired/merged into the main Azure Speech overview as the service surface has evolved (current Microsoft Learn navigation redirects it to the Speech overview page). Treat detailed speaker-recognition API specifics as lower priority for current exam versions, but understand the underlying concepts below, since speaker differentiation still appears via diarization in STT and related voice-identity scenarios.

Core concepts to know conceptually

  • Speaker verification — confirms whether an audio sample matches a specific enrolled speaker ("is this person who they claim to be?") — a 1:1 comparison, used for voice-based authentication.
  • Speaker identification — determines which enrolled speaker (from a group) produced a given audio sample — a 1:N comparison, used to attribute speech to a known set of people.
  • Diarization (covered in Section 2) is the related but distinct capability of separating/labeling anonymous speakers ("Speaker 1", "Speaker 2") within a single recording without needing pre-enrolled voice profiles — this is the capability most likely to be tested today within the STT feature set.
Must know: Don't confuse diarization (labels anonymous speakers within one recording, no enrollment needed, part of STT) with speaker verification/identification (matches audio against enrolled known-speaker voice profiles for authentication/attribution).

8. Resources, Regions & Pricing Basics

  • All Speech capabilities (STT, TTS, translation, Voice Live, custom speech/voice) are provisioned through a single Speech resource or a multi-service Azure AI Foundry resource — you don't need separate resources per feature.
  • Availability varies by region; some capabilities (e.g., custom speech audio-data training, certain Voice Live models/streaming transcription variants) require specific regions with dedicated hardware — always check the regions table for a given feature before assuming global availability.
  • Containers are available for several Speech features so you can run recognition/synthesis at the edge or disconnected from the cloud, for data-residency or offline needs.
  • Billing models differ by feature:
    • STT: typically billed per audio-hour/minute processed (real-time, fast, or batch).
    • TTS: billed per character of input text/SSML (see CJK double-counting rule above).
    • Custom voice: billed for training compute-hours plus endpoint hosting hours; personal voice adds per-day profile storage billing.
    • Custom speech: billed for model usage/endpoint hosting, and for training if the base model is from Oct 2023 or later.
Must know: A single Speech/Foundry resource exposes STT, TTS, translation, and Voice Live together; always double-check regional availability before designing a solution around custom speech training, Voice Live model choice, or streaming-specific features, since not every capability ships in every region.

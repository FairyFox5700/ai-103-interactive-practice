1. The Azure Language Resource & Core Model

Azure AI Language (branded in current docs as "Azure Language in Foundry Tools") is a single cloud resource that bundles many NLP capabilities — you do not provision a separate resource per feature. Create one Language (or multi-service Azure AI services) resource and it grants a key and endpoint URL used to authenticate every REST/SDK call.

Typical workflow (applies to almost every Language feature)

  1. Create the Language resource → get key + endpoint.
  2. Call the feature via REST API or an Azure SDK client library (C#, Java, JavaScript, Python).
  3. Authenticate the request using the key/endpoint (or Microsoft Entra ID for enterprise scenarios).
  4. Batch requests: you can combine multiple features (e.g., NER + sentiment + PII) into a single asynchronous batch API call.
  5. Most no-code exploration happens in Microsoft Foundry (ai.azure.com), which lets you try features on sample or your own text without writing code.

Core vs. Legacy capability tiers

Microsoft now groups Language features into two tiers — know this distinction, it is an easy exam trap:

TierMeaningFeatures
Core capabilitiesActively developed; recommended for new projectsPII detection, Language detection, Named Entity Recognition (prebuilt & custom), Text Analytics for Health
Legacy capabilitiesStable/supported for existing workloads only — not recommended as the foundation for new buildsConversational Language Understanding (CLU), Custom text classification, Entity linking, Key phrase extraction, Orchestration workflow, Question answering, Sentiment analysis & opinion mining, Summarization
Retirement alert: Several "legacy" features (Key phrase extraction, Sentiment/Opinion mining, Summarization, CLU, Custom Question Answering) are scheduled to retire from Azure Language on March 31, 2029. Microsoft's guidance for new projects is to use Microsoft Foundry models (generative LLMs) instead. For the exam, assume prebuilt/legacy Language APIs are still the testable baseline, but be ready for questions contrasting them with Foundry/LLM-based approaches.
Must know: One Language resource (key + endpoint) authenticates all features — you don't need a new resource per capability, and a multi-service "Azure AI services" resource also covers Language.

2. Named Entity Recognition (NER)

NER identifies and categorizes entities in unstructured text — people, places, organizations, dates, quantities, URLs, emails, etc. It is a core capability.

  • Prebuilt NER: fixed, preset list of recognized entity categories — zero training required, call the API and get labeled spans back.
  • Custom NER (CNER): train a model on your own labeled text to recognize domain-specific entity categories not in the prebuilt list (e.g., "PolicyNumber", "PartSKU").
  • Output includes entity text, category/subcategory, character offset, length, and a confidence score.

Entity linking

A related preconfigured feature: disambiguates identified entities and links them to a knowledge base (Wikipedia), useful when the same name could refer to multiple real-world entities.

Use prebuilt NER for common categories out-of-the-box (Person, Location, Organization, DateTime, Quantity, Email, URL, etc.). Reach for custom NER only when you need categories specific to your domain/business.
Must know: Prebuilt NER needs no training data; Custom NER requires labeled examples and a train/evaluate/deploy cycle, same as CLU and custom text classification.

3. PII / Sensitive Information Detection

PII detection identifies, classifies, and can redact sensitive data (names, SSNs, phone numbers, credit cards, health identifiers, etc.) across three distinct feature types that share the same model family but differ by input shape:

Feature typeInputProcessingBest for
Text PIIRaw text stringsSynchronousPrompts, logs, tickets, app fields
Conversation PIITurn-based chat / call transcriptsAsynchronous (job-based)Contact centers, meetings, voice transcripts
Document-based PIINative files (.pdf, .docx, .txt)Asynchronous (job-based)Compliance pipelines, document sharing — preserves file structure, returns redacted file + JSON metadata

All three return structured output with entity categories, confidence scores, and redacted text/documents. PII detection also supports a preview synthetic replacement / anonymization mode (replace PII with realistic-looking fake values instead of masking with ***).

PII and Language detection are the two "core" prebuilt features most directly aligned with everyday compliance scenarios on the exam — expect scenario questions like "redact SSNs from chat transcripts before storage" → Conversation PII.
Must know: Choose the PII feature type by input shape, not by data sensitivity: single strings → Text PII; multi-turn chat/call transcripts → Conversation PII; whole files (PDF/DOCX) → Document-based PII (async, preserves document fidelity).

4. Key Phrase Extraction & Language Detection

Key phrase extraction

Evaluates unstructured text and returns the main concepts/topics as a flat list of phrases (not full sentences). Example: "The food was delicious and the staff were wonderful" → ["food", "wonderful staff"]. No customization — analysis is "as-is."

Language detection

A core capability. Detects the dominant language of input text across 100+ languages/dialects and returns: language name, ISO 639-1 code, confidence score, plus optional script detection (ISO 15924 code) for languages written in multiple scripts (e.g., Kazakh in Cyrillic vs. Latin).

  • Ambiguous content handling: pass an ISO 3166-1 alpha-2 country/region hint to disambiguate words common to multiple languages (e.g., "communication" is valid English and French — hinting "FR" nudges detection toward French).
Must know: Language detection runs before most other text analytics in a pipeline — many multilingual solutions call it first to pick the right model/translation path. It returns a confidence score and can report script separately from language.

5. Sentiment Analysis & Opinion Mining

Sentiment analysis labels text as positive, neutral, or negative at both the document and sentence level, each with confidence scores (0–1) across all three labels.

Opinion mining (a.k.a. aspect-based sentiment analysis) is an optional, more granular extension of sentiment analysis: it links sentiment to specific aspects (e.g., product/service attributes) and their associated opinion words. Example: "The food was great, but the service was slow" → aspect "food" = positive, aspect "service" = slow/negative.

Sentiment analysis & opinion mining retire from Azure Language on March 31, 2029. Microsoft directs new projects to Foundry models instead — know this fact for "which approach should you use for a brand-new project" questions.
Must know: Opinion mining is a sub-feature you explicitly enable on top of sentiment analysis to get aspect-level (not just whole-sentence) sentiment — it doesn't replace sentence/document sentiment, it augments it.

6. Summarization

Summarization combines generative LLMs and task-optimized encoder models and supports three input genres: plain text, conversations (incl. audio-derived transcripts), and native documents (Word/PDF/plain text in original format).

ApproachHow it worksOutput
ExtractiveSelects/ranks the most salient original sentences from the source textVerbatim sentences + rank score + position/offset info; you choose how many sentences
AbstractiveGenerates new, concise sentences that paraphrase the source (not verbatim)Novel summary text(s) + the contextual input range each was generated from; long input may be segmented into multiple summaries

Document vs. conversation summarization

  • Text/document summarization: plain text blocks or native documents; supports both extractive and abstractive modes; jobs are async and results retrievable for 24 hours before being purged.
  • Conversation summarization: accepts multi-turn conversational input (chat or speech-derived transcripts); can produce issue/resolution summaries, chapter titles, recaps — tuned for meeting/call-center scenarios.
Exam trap: extractive = "copy the best sentences" (traceable, auditable, good for compliance where you must cite the original wording); abstractive = "rewrite in new words" (more fluent but can hallucinate — generative/LLM-based).
Summarization also retires March 31, 2029 in favor of Microsoft Foundry models — but for the current exam version, know both extractive and abstractive mechanics and their distinct output shapes.
Must know: Extractive summarization returns original sentences + a rank score; abstractive summarization returns newly generated text + the input range used — if a question emphasizes "must use exact original wording," the answer is extractive.

7. Conversational Language Understanding (CLU)

CLU is the custom natural-language-understanding feature used to build models that predict the intent of an utterance and extract entities from it. CLU only understands input — it performs no actions itself; your application/bot acts on the predicted intent/entities.

LUIS is retired. Conversational Language Understanding is its direct successor and the service you should know for AI-103 — any exam reference to "replace LUIS" or "migrate from LUIS" points to CLU. (CLU itself is now also flagged as a "legacy" capability retiring March 31, 2029, with Microsoft Foundry models as the long-term direction — but CLU remains the tested successor-to-LUIS concept.)

Key terminology (glossary)

TermDefinition
UtteranceA natural-language input/phrase a user might type or say
IntentThe task/goal the user wants (e.g., "BookFlight", "PayBill")
EntityA word/phrase in the utterance that carries information needed to fulfill the intent (can have sub-entities, e.g., Address → Street/City/Zip)
List entityA fixed, closed set of words + synonyms; matched exactly regardless of context (e.g., size = small/medium/large)
ProjectThe workspace where you build/label/train a CLU model
Model / Training / DeploymentYou label utterances → train a model → evaluate (precision/recall/F1) → deploy to a Runtime API endpoint for predictions
OverfittingModel memorizes training examples instead of generalizing to new utterances

Two build paths

  1. LLM-powered quick deploy: define intents + natural-language descriptions (no labeling needed) → deploy → the LLM predicts intents/prebuilt entities directly.
  2. Custom machine-learned model: define schema (intents + entities) → label utterances → train → evaluate → improve → deploy → predict via Runtime API. Label quality directly drives model quality.

Common use cases

  • Multi-turn conversations with entity "slot filling" (progressively collect required info, e.g., booking systems)
  • End-to-end conversational bots (retail/order bots)
  • Human-assistant / HR / enterprise chatbots
  • Command-and-control apps paired with speech-to-text (e.g., "play", "stop", "turn off the lights")

Orchestration workflow

A separate custom feature that sits above CLU and Question Answering: it routes an incoming utterance to the correct underlying CLU project or Question Answering knowledge base ("skill") when you have multiple specialized models (e.g., calendar skill vs. FAQ skill in one enterprise bot).

Must know: CLU = successor to LUIS, for intent + entity prediction only — it never executes actions. If a scenario needs to route between multiple CLU projects and a Question Answering KB, the answer is Orchestration workflow.

8. Question Answering (Custom Question Answering, CQA)

Custom question answering builds a knowledge base from FAQs, manuals, and documents to power chat bots / virtual assistants that answer natural-language questions with accurate, sourced answers.

Key capabilities

  • Knowledge base creation — import from URLs, files, documents; auto-extracts Q/A pairs from structured and semi-structured sources.
  • Multi-turn conversations — guided follow-up prompts to navigate complex topics.
  • Metadata filtering — tag answers (content type, domain, freshness) to scope responses contextually.
  • Active learning — improves ranking/answers over time using real usage data.
  • Deep learning ranking — combines Azure AI Search with NLP re-ranking for best-answer selection.

Lifecycle

  1. Create a project / knowledge base (Microsoft Foundry classic, low-code, supports markdown + chit-chat personality layers)
  2. Test & refine in the test interface
  3. Deploy → publishes a REST API endpoint
  4. Integrate → client apps query and get JSON answers with confidence scores and follow-up prompts

Deploys easily to Azure Bot Service for a ready-made conversational front end.

Custom Question Answering retires March 31, 2029 — Foundry is the forward-looking replacement, but CQA concepts (KB from FAQs, confidence scores, multi-turn prompts) remain testable.
Must know: Question Answering ≠ CLU. CLU predicts intent/entities from open-ended utterances for custom logic; Question Answering retrieves a best-matching pre-authored answer from a curated knowledge base (FAQ-style) with a confidence score.

9. Customization: Custom NER & Custom Text Classification

Beyond CLU, two other "custom" Language features follow the same labeling → training → evaluation → deployment lifecycle:

  • Custom Named Entity Recognition (CNER): train a model to extract domain-specific entity categories not covered by prebuilt NER (e.g., compliance clause types, part numbers, policy IDs).
  • Custom text classification: classify unstructured documents into your own custom classes/labels — supports single-label (one class per document) and multi-label (several classes per document) classification projects.

Typical steps for any custom project: define schema/labels → upload & label data → train → review evaluation metrics (precision, recall, F1) → deploy → call via the runtime/prediction API.

Domain-specific tasks called out in the exam objective — e.g., "compliance summarization" or "domain-specific extraction" — map to combining Custom NER / custom classification (structured, labeled training) with Summarization or LLM prompting (for unstructured, flexible output).
Must know: Precision = correctly predicted positives ÷ all predicted positives; Recall = correctly predicted positives ÷ all actual positives; F1 = harmonic balance of both. These metrics are evaluated identically across Custom NER, Custom text classification, and CLU.

10. Generative/LLM-Based Extraction vs. Prebuilt Language APIs

Microsoft's current direction (reflected across nearly every Language doc page) is to steer new projects toward Microsoft Foundry generative models for text analysis tasks — entities, topics, summaries, and structured JSON — using prompt engineering instead of (or alongside) the classic prebuilt REST APIs.

ApproachStrengthsTrade-offs
Prebuilt Language APIs (NER, key phrase, sentiment, summarization, PII)Deterministic, fast, cheap, no prompt design needed, consistent schema/confidence scores, good for compliance/auditabilityFixed entity categories (unless you go custom); less flexible output shaping; several features scheduled to retire by 2029
Generative/LLM prompting (via Foundry models / Azure OpenAI)Flexible — can extract arbitrary entities/topics, produce abstractive summaries, or return structured JSON matching any schema you define in the prompt; can combine extraction + reasoning in one callNon-deterministic without careful prompting/temperature control; costs more per call; needs evaluation/guardrails; less "out of the box" confidence scoring

Foundry Tools framing

Azure Language capabilities are also exposed as callable tools in the Microsoft Foundry Tool Catalog (as a remote MCP server, or self-hosted locally) — meaning an agent built in Foundry can invoke NER/PII/summarization/etc. as a tool call rather than you writing direct REST calls. This is the bridge between "classic Language APIs" and "LLM agents": an agent's orchestrating LLM decides when to call a Language tool (e.g., redact PII) versus when to generate an answer itself.

Exam framing: when a scenario needs flexible, instruction-following extraction into a custom JSON schema, or combines extraction with summarization/translation/reasoning in one step, lean toward generative/LLM prompting via Foundry. When a scenario needs fast, deterministic, auditable entity/sentiment/PII detection with built-in confidence scores, the prebuilt Language API is still the right call.
Must know: Prebuilt Language APIs return fixed schemas with confidence scores and are optimized for deterministic, compliance-friendly analysis; generative/LLM prompting (Foundry models) trades some determinism for flexible, custom-schema extraction and can be invoked as a tool from an agent.

11. Exam Cheat Sheet — Quick Facts

  • One Language resource (key + endpoint) authenticates all Language features; multi-service Azure AI services resource also works.
  • Core capabilities (new-project recommended): PII detection, Language detection, NER (prebuilt & custom), Text Analytics for Health.
  • Legacy capabilities (supported, not for new foundations): CLU, Custom text classification, Entity linking, Key phrase extraction, Orchestration workflow, Question answering, Sentiment/opinion mining, Summarization.
  • Several legacy features retire March 31, 2029 → migrate to Microsoft Foundry models.
  • CLU replaced LUIS — intents + entities + utterances; trains/evaluates/deploys like other custom features; does not take action itself.
  • Opinion mining = aspect-based add-on to sentiment analysis (not a standalone replacement).
  • Extractive summarization = original sentences + rank score; abstractive = new generated text + input range.
  • PII feature choice is driven by input shape: Text PII (strings), Conversation PII (chat/transcripts), Document-based PII (native files, async).
  • Question Answering = FAQ/knowledge-base retrieval with confidence score; different from CLU's open-ended intent prediction.
  • Orchestration workflow routes between multiple CLU projects and/or Question Answering knowledge bases.
  • Custom NER / custom text classification / CLU all share the same lifecycle: label → train → evaluate (precision/recall/F1) → deploy → predict.
  • Generative/LLM prompting (Foundry models) favored for flexible, custom-JSON extraction; prebuilt APIs favored for deterministic, auditable results; Language capabilities can be called as agent tools via the Foundry Tool Catalog / MCP server.

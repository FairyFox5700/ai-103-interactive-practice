1. What Is Microsoft Foundry

Microsoft Foundry (the rebrand of Azure AI Foundry / Azure AI Studio) is a unified platform for building, deploying, and governing agents, models, and tools under one Azure resource provider namespace (Microsoft.CognitiveServices).

Core value proposition

  • One management plane: unified RBAC, networking, and Azure Policy across agents, models, and tools.
  • Model catalog: 10,000+ models (Microsoft, OpenAI, Anthropic, Meta, Mistral, Cohere, Hugging Face, DeepSeek, NVIDIA NIMs, and more).
  • Agent Service: managed hosting/runtime for agents of any complexity (declarative to full custom code).
  • Enterprise-ready: built-in tracing, evaluations, content filters, Entra ID identity, private networking.

Two portal experiences (exam-relevant distinction)

ExperienceProject modelStatus
Foundry (new)Foundry resource → Foundry project (subresource of Microsoft.CognitiveServices/accounts)Current, recommended default for new builds
Foundry (classic)Hub → multiple hub-based projects (Azure ML–style, ties to AI Hub resource)Legacy; still used for serverless API endpoints & managed compute deployments
Tip: If you're upgrading an existing Azure OpenAI resource, you can upgrade it in place to a Foundry resource while keeping the same endpoint and API keys — no redeployment needed.
Must know: The exam may test the resource hierarchy terminology — a Foundry resource (kind: AIServices) is the top-level governance boundary; a Foundry project is a subresource under it (accounts/projects), not a separate top-level resource. Hub-based projects are the older, classic-portal-only model.

2. Foundry Models & Catalog

Model categories

  • Foundry Models sold by Azure: Microsoft hosts and sells these (incl. Azure OpenAI models). Microsoft support, enterprise SLAs, deep Azure integration, internal Responsible AI review, some offer fungible provisioned throughput (quota shared flexibly across models).
  • Foundry Models from partners & community: the majority of the catalog (Anthropic Claude, Hugging Face models, Meta Llama, Mistral, Cohere, industry-specific models). Diverse capabilities; support/SLA varies by provider.

Model types to recognize for the exam

  • Foundation / Large Language Models (LLMs): general-purpose text generation, reasoning, chat (e.g., GPT-4o family).
  • Small Language Models (SLMs): lightweight, lower-latency/cost, good for edge or narrow tasks (e.g., Phi family).
  • Reasoning models: optimized for multi-step/chain-of-thought problem solving.
  • Multimodal models: accept/produce combinations of text, image, audio (vision + text, speech-to-speech realtime models like GPT-Realtime).
  • Domain-specific / industry models: e.g., Saifr, Rockwell, Bayer, Cerence — require managed compute deployment.
  • Embedding models: used for vector search / RAG grounding scenarios.

Foundry Tools (formerly "Cognitive Services" / AI Services)

Prebuilt, task-specific APIs you compose alongside models: Azure AI Content Safety, Azure AI Search (vector/keyword/hybrid retrieval for grounding), Speech, Vision, Language, Content Understanding, Translator (Foundry-resource scope only).

Tip: Choosing a model for the exam = match task → model type. Simple classification/low-latency → SLM. Multi-step agentic reasoning → reasoning model. Image+text grounding → multimodal. Need to search your own documents → pair any LLM with Azure AI Search for vector/RAG grounding, not a bigger model.
Must know: You are responsible for reviewing each model's model card, selecting an appropriate model for your use case, and layering Content Safety yourself — Microsoft's Responsible AI review of "sold by Azure" models does not guarantee risk mitigation for your specific application.

Deploying a catalog model (CLI)

From the catalog, a model becomes callable by creating a deployment on your Foundry resource. The Azure CLI is the fastest non-portal way to do this for scripted/repeatable setups:

Azure CLI 
az cognitiveservices account deployment create \
  --name my-foundry-resource \
  --resource-group rg-ai103-demo \
  --deployment-name gpt-4o-mini \
  --model-name gpt-4o-mini \
  --model-version "2024-07-18" \
  --model-format OpenAI \
  --sku-capacity 10 \
  --sku-name GlobalStandard

List what is already deployed on the resource (useful before picking a model= value in SDK/REST calls):

Azure CLI 
az cognitiveservices account deployment list \
  --name my-foundry-resource \
  --resource-group rg-ai103-demo \
  --output table

3. Projects, Hubs & Architecture

Resource hierarchy (new Foundry portal)

  • Foundry resource (Microsoft.CognitiveServices/accounts, kind AIServices) — top-level: model deployments, security/networking settings, connections. This is the governance/administrative boundary.
  • Foundry project (accounts/projects subresource) — development boundary: agents, evaluations, files, scoped per team/use case. Reuses the parent's model deployments and connections — no repeated IT setup per project.
  • Connected resources — Storage, Key Vault, Azure AI Search: independent Azure resources, each with its own governance boundary (you manage their networking/access separately).

Azure resource providers in the AI family

Resource providerPurposeExample services
Microsoft.CognitiveServicesAgentic/GenAI app dev, prebuilt + custom modelsFoundry, Azure OpenAI, Speech/Vision/Language in Foundry Tools
Microsoft.SearchKnowledge retrieval over your dataAzure AI Search

When to use which setup

  • Single developer / exploration: one Foundry resource + one project (recommended default).
  • Multi-team org: one Foundry resource with multiple projects — isolated workspaces, shared model deployments, centralized governance.
  • Compliance-driven: Foundry resource model supports private networking, customer-managed keys, Azure RBAC scoping at both resource and project levels.
  • Pure inference only (no agents/evals): a standalone Azure OpenAI resource may suffice.

Creating a project

Supported surfaces: Foundry portal (fastest, auto-creates the Foundry resource), Python SDK (azure-mgmt-cognitiveservices + DefaultAzureCredential), Azure CLI, or ARM/Bicep templates (for org-mandated naming/tag/security policies).

Tip: For custom Azure Policy requirements (naming conventions, security controls, cost tags), use the Azure portal or templates instead of the Foundry portal quick-create flow.

Model deployment types (data-processing scope)

Deployment typeData processingBilling
Global StandardCross-region, Azure-managedPay-per-token
Global ProvisionedCross-regionHourly reserved capacity (PTU)

Monitoring scope

  • Resource-level metrics: token consumption, model latency, request counts, error rates across all projects.
  • Project-level metrics: evaluation run outcomes, agent invocation counts, file operation activity.
  • Diagnostic logging: route to Log Analytics, Storage, or Event Hubs via Azure Monitor diagnostic settings.
Must know: Not every API is available at project scope — some (e.g., Translator) are available only at the Foundry resource level. Plan architecture based on which API scope your workload actually needs before assuming "project-level" covers everything.

Provisioning as code (Bicep)

For org-mandated naming/tags/policy, define the Foundry resource and project declaratively instead of using the quick-create portal flow:

Scenario: A regulated customer requires every Foundry deployment to be created only through reviewed templates, with mandatory tags and no public network access, across multiple subscriptions.
Answer: Provision the Foundry resource and projects with ARM/Bicep templates (not the Foundry portal quick-create flow), setting publicNetworkAccess: 'Disabled' and required tags in the template, then enforce this via Azure Policy — the portal quick-create path does not support mandatory naming/tag/security policy enforcement.

Calling a Standard deployment keylessly (REST)

Standard deployment is the only option supporting Entra ID bearer tokens instead of API keys — get a token with az account get-access-token and call the Responses API directly:

REST / Bash 
TOKEN=$(az account get-access-token --scope https://ai.azure.com/.default --query accessToken -o tsv)

curl -X POST "https://my-foundry-resource.services.ai.azure.com/api/projects/my-project/openai/v1/responses" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
        "model": "gpt-4o-mini",
        "input": "Summarize the AI-103 deployment options table in two sentences."
      }'
Scenario: Your compliance team requires that application code never store or transmit a long-lived API key when calling a Foundry model.
Answer: Use a Standard deployment and authenticate with Microsoft Entra ID (DefaultAzureCredential in the SDK, or a bearer token from az account get-access-token for REST) — serverless API endpoints and managed compute deployments do not support keyless auth, so Standard deployment is the only option that satisfies this requirement.

5. Foundry Agent Service

A managed platform for building, deploying, and scaling AI agents — any framework, any catalog model, one entry point for inference + tools.

Three agent types (declarative → full code spectrum)

TypeBuild surfaceRuntime/computeBest for
Prompt agentsPortal, SDK, REST, Azure Developer CLI (azd)Fully managed, no code/containersFast start; production agents without custom orchestration
Voice-based prompt agentsPortal/SDK config + Voice Live connectionFully managed real-time WebSocketSpoken/call-center experiences, low latency
Hosted agentsAgent Framework, LangGraph, OpenAI Agents SDK, Anthropic SDK, custom code — shipped as container or .zipFoundry-managed container compute, autoscaleCustom orchestration, multi-agent systems, bring-your-own-code

A fourth pattern — calling the Responses API directly — creates an ephemeral agent: instructions/tools/model are assembled in your own app code per-request, with no persisted Foundry agent resource, but you still get catalog models, platform tools, and project-level observability/governance.

Agent Service components

  • Agent Runtime: hosts/scales prompt & hosted agents; manages conversations, tool calls, lifecycle.
  • Toolboxes: curated, reusable tool sets (web search, file search, code interpreter, MCP servers, custom functions) shared across agents via one managed MCP endpoint with centralized auth/governance/versioning.
  • Models: swap models (GPT-4o, Llama, DeepSeek, etc.) without changing agent code.
  • Observability: end-to-end tracing, metrics, evaluations, Application Insights integration.
  • Agent Optimizer (preview): auto-generates better instructions, skills, tool descriptions, model choices.
  • Identity & Security: Entra ID identity per agent, RBAC, content filters, VNet isolation.
  • Publishing: version agents, stable endpoints, share via Teams, Microsoft Copilot, Entra Agent Registry.

Voice agent architectures

  • Native speech-to-speech: one realtime model handles audio in/out directly — lowest latency.
  • Cascaded text model: speech recognition → text model → speech synthesis — more model/voice choice, more control, higher end-to-end latency.
Tip: Choosing an agent type on the exam = map requirement → type. "No code to maintain" → prompt agent. "Bring my own LangGraph/Agent Framework code" → hosted agent. "Phone/voice channel" → voice-based prompt agent. "Agent logic lives in my app, no Foundry resource to manage" → ephemeral agent via Responses API.
Must know: Hosted agents get an automatic, dedicated per-agent Microsoft Entra identity; prompt and voice-based prompt agents use Entra identity too but with no runtime code/container to manage at all — the exam may ask which type requires you to manage container compute (answer: hosted agents only).

Creating a prompt agent and chatting with it (Python SDK)

Uses azure-ai-projects (v2.x) against the Foundry projects API: create a project client, define the agent version, then drive a multi-turn conversation through the OpenAI-compatible client bound to that agent.

Python 
from azure.identity import DefaultAzureCredential
from azure.ai.projects import AIProjectClient
from azure.ai.projects.models import PromptAgentDefinition

FOUNDRY_PROJECT_ENDPOINT = "https://my-foundry-resource.services.ai.azure.com/api/projects/my-project"
FOUNDRY_AGENT_NAME = "support-agent"

project = AIProjectClient(
    endpoint=FOUNDRY_PROJECT_ENDPOINT,
    credential=DefaultAzureCredential(),
)

# Create (or version) the agent
project.agents.create_version(
    agent_name=FOUNDRY_AGENT_NAME,
    definition=PromptAgentDefinition(
        model="gpt-4o-mini",
        instructions="Answer only using the grounded knowledge base. Be concise.",
    ),
)

# OpenAI-compatible client pre-bound to the agent
openai = project.get_openai_client(agent_name=FOUNDRY_AGENT_NAME)

conversation = openai.conversations.create()
response = openai.responses.create(conversation=conversation.id, input="What is Foundry Agent Service?")
print(response.output_text)

follow_up = openai.responses.create(conversation=conversation.id, input="Which agent type needs no container management?")
print(follow_up.output_text)

6. RBAC & Identity

Key terminology

  • Scope: subscription, resource group, Foundry resource, Foundry project, or individual agent.
  • Role: named permission set applied at a scope.
  • Control-plane vs data-plane actions: creating deployments/projects (control) is distinct from building agents, running evaluations, uploading files (data).

Built-in Foundry roles

RoleKey capability
Foundry Agent ConsumerLeast-privilege: interact with agent endpoints only (e.g., call Responses API) — no create/modify rights.
Foundry UserReader + data actions (build/test agents). Minimum role for developers; also assign to the project's managed identity.
Foundry Project ManagerManage projects, build/develop, publish agents, conditionally assign Foundry User to others.
Foundry Account OwnerFull resource/project management, manage models, conditionally assign Foundry User/ACR/monitoring roles — cannot build in projects.
Foundry OwnerEverything above combined — highly privileged self-serve role.
Tip: These roles were renamed from Azure AI User/Owner/Account Owner/Project Manager → Foundry User/Owner/Account Owner/Project Manager. Role IDs and permissions are unchanged — only display names changed. Expect either naming on the exam.

Minimum setup for a new user

  1. Assign Foundry User to the user principal on the Foundry resource.
  2. Assign Foundry User to the project's managed identity on the Foundry resource.
  3. For quota/usage visibility, assign Cognitive Services Usages Reader at subscription scope.
Must know: Key-based authentication bypasses RBAC entirely — a valid key grants full access with no role restriction. Microsoft Entra ID authentication is required to get granular, least-privilege access control. Also: don't use generic Cognitive Services roles or Azure AI Developer (scoped to AML workspaces/hubs) for Foundry project access — use the Foundry-specific roles instead.

Assigning Foundry User to a project's managed identity (CLI)

Azure CLI 
# Get the system-assigned managed identity principal ID of the project
PRINCIPAL_ID=$(az resource show \
  --ids /subscriptions/<sub-id>/resourceGroups/rg-ai103-demo/providers/Microsoft.CognitiveServices/accounts/my-foundry-resource/projects/my-project \
  --query identity.principalId -o tsv)

# Grant Foundry User on the Foundry resource to that identity
az role assignment create \
  --assignee "$PRINCIPAL_ID" \
  --role "Foundry User" \
  --scope /subscriptions/<sub-id>/resourceGroups/rg-ai103-demo/providers/Microsoft.CognitiveServices/accounts/my-foundry-resource

# Grant a human developer Foundry User at the same scope
az role assignment create \
  --assignee "dev@contoso.com" \
  --role "Foundry User" \
  --scope /subscriptions/<sub-id>/resourceGroups/rg-ai103-demo/providers/Microsoft.CognitiveServices/accounts/my-foundry-resource
Scenario: A CI/CD service principal must be able to build and test prompt agents in a dev project, but must never be able to publish agents to production or manage the Foundry resource itself.
Answer: Assign the service principal the Foundry User role scoped to the dev project only — it grants data-plane build/test actions without publish rights (publishing requires Foundry Project Manager or higher) and without control-plane resource management rights, satisfying least privilege.

7. Networking, Quotas & Monitoring

Security mechanisms

  • Managed identity: every Foundry project has a system-assigned managed identity used for keyless access to connected resources (Storage, Key Vault, Search) and must itself be granted Foundry User on the resource.
  • Keyless (Entra ID) credentials: preferred over API keys; only supported on Standard deployment — not on serverless API or managed compute.
  • Private networking: VNet integration / private link available across all three deployment types; supports network-isolated agent, evaluation, and batch workloads.
  • Customer-managed keys (CMK): supported at the Foundry resource for encryption-at-rest compliance scenarios.
  • Azure Policy: shared provider namespace (Microsoft.CognitiveServices) means existing OpenAI/Cognitive Services policies continue to apply after upgrading to Foundry.

Quotas, scaling & cost control

  • Standard (pay-as-you-go): rate-limited by tokens-per-minute (TPM) / requests-per-minute (RPM) quota per deployment/region.
  • Provisioned Throughput Units (PTU): reserved, hourly-billed capacity for predictable latency/throughput at scale; some sold-by-Azure models support fungible PTU — quota reservation usable flexibly across multiple eligible models.
  • Managed compute: billed per-minute by compute core-hours/instance count — requires subscription compute quota.
  • Cognitive Services Usages Reader role: needed to view quota/run deployment eligibility checks without granting broader access.

Monitoring layers

LayerWhat it tracks
Foundry resource (top-level)Token consumption, model latency, request counts, error rates — across all projects
Foundry projectEvaluation run outcomes, agent invocation counts, file operation activity
Diagnostic settingsRoute logs to Log Analytics / Storage / Event Hubs for retention & analysis
Agent observabilityEnd-to-end tracing of agent decisions/tool calls, evaluations, Application Insights integration
Tip: When a scenario mentions "need to see cross-project usage and errors" → resource-level metrics. "Need to see how one team's agents perform" → project-level metrics.
Must know: Keyless/Entra ID auth, custom content filtering, and all three data-processing scopes (regional/data-zone/global) are available only with Standard deployment in a Foundry resource — this is a common "which deployment option supports X" trap.

8. Responsible AI & Safety

Shared responsibility

  • Microsoft performs an internal Responsible AI review for models sold by Azure and publishes transparency/model cards — but this does not guarantee risk mitigation for your specific app.
  • You are responsible for: complying with applicable law, reviewing model cards, selecting appropriate models, and implementing safeguards (e.g., Azure AI Content Safety) to comply with Microsoft's Acceptable Use Policy and Enterprise AI Services Code of Conduct.

Guardrails & safety tooling

  • Content filters: built into Standard/serverless deployments to block harmful content categories (hate, violence, sexual, self-harm) at configurable severity thresholds; custom content filtering only on Standard deployment.
  • Evaluations / safety evaluators: built-in evaluators assess groundedness, relevance, coherence, and safety (e.g., jailbreak/harmful content risk) for both models and agents before and after deployment.
  • Tracing/observability: end-to-end trace logs capture agent reasoning steps, tool calls, and model responses — supports provenance review and audit.
  • Agent oversight controls: RBAC at the agent scope, Entra identity per agent (hosted agents), tool-access governance via Toolboxes (centralized auth/versioning so you control which tools an agent can call).
  • Approval/publishing workflow: agents are versioned and published through controlled channels (Teams, Copilot, Entra Agent Registry) rather than ad hoc, supporting governance over what reaches production.

Agent-specific risk controls

  • Scope RBAC at the agent level to grant endpoint access to one agent without exposing all agents in a project (narrowest practical scope).
  • Use Foundry Agent Consumer for principals/apps that only need to call an agent, not modify it — reduces blast radius.
  • Constrain tool access through curated Toolboxes rather than giving agents unrestricted tool/function access.
Tip: When a question describes "ensuring an agent's model outputs are safe before rollout" think safety evaluators; when it describes "blocking harmful content at inference time" think content filters; when it describes "understanding why an agent made a decision after the fact" think tracing/observability.
Must know: Content filtering is not available at all on managed compute deployments — if a scenario requires content safety guardrails, managed compute is the wrong deployment choice.

Applying a custom content filter to a Standard deployment (REST)

REST / Bash

  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
        "properties": {
          "raiPolicyName": "contoso-strict-filter"
        }
      }'

Running a safety evaluator before rollout (Python)

Python 
from azure.ai.evaluation import evaluate, ViolenceEvaluator, GroundednessEvaluator
from azure.identity import DefaultAzureCredential

model_config = {"azure_endpoint": "https://my-foundry-resource.services.ai.azure.com", "azure_deployment": "gpt-4o-mini"}

result = evaluate(
    data="eval_dataset.jsonl",
    evaluators={
        "violence": ViolenceEvaluator(credential=DefaultAzureCredential(), azure_ai_project=FOUNDRY_PROJECT_ENDPOINT),
        "groundedness": GroundednessEvaluator(model_config=model_config),
    },
)
print(result["metrics"])
Scenario: Before promoting a new agent version to production, the team must confirm its answers stay grounded in the retrieved documents and don't introduce unsafe content, and they want this check automated in the release pipeline.
Answer: Add a safety/groundedness evaluation step (e.g., GroundednessEvaluator, built-in safety evaluators) to the CI/CD pipeline that runs against a representative evaluation dataset before the agent version is published — this is distinct from runtime content filters, which block harmful output live rather than validating quality/groundedness pre-release.

9. SDKs, CLI & CI/CD Integration

Developer surfaces

SurfaceBest for
Foundry portalExploring models, prototyping prompts, building prompt agents with no code
SDKs (Python, C#, JavaScript, Java)Building applications; code-first agent definitions for CI/CD integration
Azure Developer CLI (azd)Keep agent definitions in source control; deploy/invoke via pipeline commands

Code-first / CI/CD pattern for agents

  • Define prompt agents programmatically (SDK/REST) instead of only in the portal — enables version control, code review, and automated rollout.
  • Hosted agents ship as a container image or .zip of source; Foundry builds the container for you from a .zip, enabling standard build pipelines.
  • Use managed identity (not keys) in pipeline/service-to-service calls for keyless, auditable authentication.
  • Promote agent versions across environments (dev/test/prod projects) using consistent RBAC roles (Foundry Project Manager to publish, Foundry User to build/test).
Tip: "Portal-first" prototyping → "Code-first" productionization is the expected maturity path Microsoft documents for prompt agents — expect a scenario question on moving from manual portal configuration to pipeline-driven deployment.
Must know: Only Foundry Project Manager (or higher) can publish agents — Foundry User can build/test but not publish, a frequent "least privilege for CI/CD service principal" exam trap.

Promoting an agent version in a pipeline (azd + GitHub Actions)

YAML 
name: deploy-agent
on:
  push:

Hands-On Patterns

Worked examples that tie the model catalog, Agent Service, tools, and governance concepts above into one end-to-end flow.

Pattern 1 — Full agent + tool registration + run polling (Python)

Registers a function tool, lets the agent decide to call it, and polls the response until complete — the pattern behind most "agent calls a custom function" exam scenarios.

Python 
from azure.identity import DefaultAzureCredential
from azure.ai.projects import AIProjectClient
from azure.ai.projects.models import PromptAgentDefinition, FunctionTool

FOUNDRY_PROJECT_ENDPOINT = "https://my-foundry-resource.services.ai.azure.com/api/projects/my-project"

project = AIProjectClient(endpoint=FOUNDRY_PROJECT_ENDPOINT, credential=DefaultAzureCredential())

def get_order_status(order_id: str) -> str:
    """Looks up an order status from the fulfillment system."""
    return f"Order {order_id} shipped on 2026-11-10."

order_tool = FunctionTool(functions={get_order_status})

agent = project.agents.create_version(
    agent_name="order-support-agent",
    definition=PromptAgentDefinition(
        model="gpt-4o-mini",
        instructions="Help customers check order status. Use the get_order_status tool when an order ID is given.",
        tools=order_tool.definitions,
    ),
)

openai = project.get_openai_client(agent_name="order-support-agent")
conversation = openai.conversations.create()

response = openai.responses.create(conversation=conversation.id, input="Where is order 48213?")

# Resolve any pending tool calls, then poll until the run has a final answer
while response.status in ("queued", "in_progress", "requires_action"):
    if response.status == "requires_action":
        outputs = order_tool.execute(response.required_action)
        response = openai.responses.submit_tool_outputs(response_id=response.id, tool_outputs=outputs)
    else:
        response = openai.responses.retrieve(response.id)

print(response.output_text)

Pattern 2 — Keyless REST flow: deploy, then call (CLI + Bash)

Combines IaC-free provisioning with a keyless runtime call — useful for quick scripted smoke tests of a new deployment.

REST / Bash 
# 1. Deploy the model
az cognitiveservices account deployment create \
  --name my-foundry-resource --resource-group rg-ai103-demo \
  --deployment-name gpt-4o-mini --model-name gpt-4o-mini \
  --model-version "2024-07-18" --model-format OpenAI \
  --sku-capacity 10 --sku-name GlobalStandard

# 2. Get a keyless bearer token (no API key stored anywhere)
TOKEN=$(az account get-access-token --scope https://ai.azure.com/.default --query accessToken -o tsv)

# 3. Smoke-test the new deployment
curl -s -X POST "https://my-foundry-resource.services.ai.azure.com/api/projects/my-project/openai/v1/responses" \
  -H "Content-Type: application/json" -H "Authorization: Bearer $TOKEN" \
  -d '{"model":"gpt-4o-mini","input":"Reply with OK if you can read this."}' | jq .output_text

Pattern 3 — Governed provisioning: Bicep + least-privilege RBAC in one script

Ties infrastructure-as-code (section 3/7) to RBAC (section 6) so a new project is both compliant and immediately usable by its own managed identity.

Azure CLI 
# Deploy the Bicep template from section 3 (Foundry resource + project)
az deployment group create --resource-group rg-ai103-demo --template-file foundry.bicep

# Grant the new project's managed identity least-privilege access to itself
PRINCIPAL_ID=$(az resource show \
  --ids /subscriptions/<sub-id>/resourceGroups/rg-ai103-demo/providers/Microsoft.CognitiveServices/accounts/my-foundry-resource/projects/my-project \
  --query identity.principalId -o tsv)

az role assignment create \
  --assignee "$PRINCIPAL_ID" --role "Foundry User" \
  --scope /subscriptions/<sub-id>/resourceGroups/rg-ai103-demo/providers/Microsoft.CognitiveServices/accounts/my-foundry-resource

# Enable diagnostics so the new project is observable from day one
az monitor diagnostic-settings create --name foundry-diagnostics \
  --resource /subscriptions/<sub-id>/resourceGroups/rg-ai103-demo/providers/Microsoft.CognitiveServices/accounts/my-foundry-resource \
  --workspace /subscriptions/<sub-id>/resourceGroups/rg-ai103-demo/providers/Microsoft.OperationalInsights/workspaces/law-ai103 \
  --logs '[{"category":"Audit","enabled":true}]' --metrics '[{"category":"AllMetrics","enabled":true}]'

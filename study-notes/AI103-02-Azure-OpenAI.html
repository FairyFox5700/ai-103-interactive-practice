1. Platform & the "Microsoft Foundry" rebrand

Azure OpenAI Service documentation has been folded into Microsoft Foundry (formerly "Azure AI Foundry" / "Azure AI Studio"). Conceptually, "Azure OpenAI" is now a Foundry Models catalog category — OpenAI models sold directly by Azure — consumed through a Foundry resource and a Foundry project.

  • Foundry resource — the Azure resource (ARM), analogous to the old "Azure OpenAI resource." Has an endpoint like https://YOUR-RESOURCE-NAME.openai.azure.com/openai/v1/.
  • Foundry project — a logical workspace inside/under a resource used to organize deployments, agents, evaluations, and connections. Existing hub-based ("classic") projects still work via the Foundry (classic) portal, but new investment is in the new Foundry portal project model.
  • Foundry portal — https://ai.azure.com — unified UI for deploying models, building agents, running evaluations, and configuring content filters/guardrails.
  • You can upgrade an existing Azure OpenAI resource to a Foundry resource in place, preserving the endpoint, API keys, and deployments.
  • Foundry unifies agents, models, and tools under one RBAC/networking/policy model, with built-in tracing, monitoring, and evaluation.
For the exam, treat "Azure OpenAI," "Azure OpenAI in Microsoft Foundry," and "Foundry Models (OpenAI)" as the same underlying service — just evolving branding. API shapes (Chat Completions, Responses, Assistants) are unchanged.
Must know: A Foundry/Azure OpenAI resource is the billing/endpoint boundary; a deployment is a named instance of a specific model version inside that resource that your app actually calls (you always call a deployment name, not a raw model name, in Chat Completions).

Minimal working example — basic chat completion

Every Foundry/Azure OpenAI resource exposes an OpenAI-compatible endpoint at https://YOUR-RESOURCE-NAME.openai.azure.com/openai/v1/ that works directly with the standard openai SDK (no Azure-specific client required) by overriding base_url.

Python 
import os
from openai import OpenAI

client = OpenAI(
    base_url="https://YOUR-RESOURCE-NAME.openai.azure.com/openai/v1/",
    api_key=os.getenv("AZURE_OPENAI_API_KEY"),
)

response = client.chat.completions.create(
    model="gpt-4o-mini",  # this is the DEPLOYMENT NAME, not the raw model name
    messages=[
        {"role": "system", "content": "You are a concise technical assistant."},
        {"role": "user", "content": "Summarize this contract clause in one sentence."},
    ],
    temperature=0.2,
)
print(response.choices[0].message.content)
curl / REST 
curl "https://YOUR-RESOURCE-NAME.openai.azure.com/openai/v1/chat/completions" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $AZURE_OPENAI_API_KEY" \
  -d '{
        "model": "gpt-4o-mini",
        "messages": [{"role": "user", "content": "Say hello in French"}],
        "temperature": 0.2
      }'

Scenario: A contact-center app calls GPT-4o for live call summarization. During a product launch, call volume triples overnight and users start reporting slow, inconsistent response times that must be fixed with a predictable, guaranteed SLA — cost is secondary to reliability.
Recommended answer: Migrate the deployment from Global Standard to Provisioned Throughput Units (PTU).
Rationale: Global Standard shares capacity across tenants, so latency/throughput varies under load spikes. PTU reserves dedicated capacity for the deployment, giving consistent, guaranteed latency and throughput regardless of other tenants' traffic — the correct tradeoff when predictability matters more than per-token cost.

3. Retrieval-Augmented Generation (RAG) / grounding your data

RAG lets a model answer using your own enterprise content instead of (or in addition to) what it learned during training — reducing hallucination and enabling up-to-date, proprietary answers with citations.

Classic pattern: "Azure OpenAI On Your Data" (retired)

Retirement notice: Azure OpenAI On Your Data (OYD) — the feature that let you point a Chat Completions call at an Azure AI Search index via the data_sources parameter / /extensions/chat/completions endpoint — retired on October 14, 2026 and is no longer supported. If you see legacy exam prep material describing "Add your data" in Azure OpenAI Studio, know that it has been replaced.

Conceptually, OYD still illustrates the RAG pattern you must understand for the exam:

  1. User query arrives at the app.
  2. App (or the service) retrieves the most relevant chunks from a knowledge store (commonly an Azure AI Search index) using vector, keyword, or hybrid (vector+keyword+semantic re-ranking) search.
  3. Retrieved chunks are inserted into the prompt as grounding context alongside the user's question and a system message instructing the model to answer only from the provided content.
  4. The model generates a grounded answer, ideally with citations back to source documents.

Current pattern: Foundry IQ Knowledge Bases + Agent Service

  • Foundry IQ introduces Knowledge Sources (e.g., a Search Index Knowledge Source wrapping an existing Azure AI Search index) attached to a Knowledge Base (KB).
  • Your app calls the KB's retrieve action directly for grounded, cited answers — replacing the old chat.completions + data_sources call.
  • Retrieval modes: auto retrieval starts lightweight and can escalate to LLM-based query planning ("agentic retrieval") if the first pass lacks grounding; answerSynthesis uses a configured model to compose the final cited answer.
  • For richer workflows (multi-tool orchestration, multi-turn conversation state, combining several knowledge sources), attach the KB to a Foundry Agent Service agent instead of calling the KB directly.
  • GA, non-preview alternative for simple extractive retrieval: Azure AI Search agentic retrieval (2026-04-01) — minimal, extractive knowledge-base retrieval where your application still manages answer generation.
Exam framing: understand RAG as a pattern — embed documents → store vectors in a search index → retrieve top-k relevant chunks → augment the prompt → generate a grounded answer with citations. The specific product name wrapping that pattern (On Your Data vs. Foundry IQ Knowledge Base vs. a custom app-level implementation) can change, but the architecture is what's tested.

Why RAG over fine-tuning for "knowing your data"?

  • RAG is for injecting fresh/private facts at query time — no retraining needed when documents change.
  • Fine-tuning changes behavior/style/format, not facts — it does not reliably teach new, retrievable factual knowledge and does not eliminate hallucination.
  • Many production systems combine both: RAG for facts + fine-tuning for tone/format/tool-use patterns.
Must know: Azure OpenAI On Your Data retired Oct 14, 2026; the supported path is a Foundry IQ Knowledge Base built on a Knowledge Source (commonly wrapping your existing Azure AI Search index), called via retrieve, optionally via an Agent Service agent — this is the concept the exam now expects for "implement RAG in an application."

Worked example — retrieve-then-generate RAG call

Python 
from azure.search.documents import SearchClient
from azure.core.credentials import AzureKeyCredential
from openai import AzureOpenAI

search_client = SearchClient(
    endpoint="https://my-search.search.windows.net",
    index_name="product-docs-index",
    credential=AzureKeyCredential("<search-key>"),
)
aoai = AzureOpenAI(
    azure_endpoint="https://my-resource.openai.azure.com/",
    api_key="<key>", api_version="2026-xx-xx",
)

query = "What is the warranty period for model X200?"

# 1. Retrieve top-k relevant chunks (hybrid vector + keyword search)
results = search_client.search(search_text=query, top=3,
                                query_type="semantic", semantic_configuration_name="default")
context = "\n\n".join(f"[Doc {i+1}] {r['content']}" for i, r in enumerate(results))

# 2. Augment the prompt with grounding context and ask for cited answers
messages = [
    {"role": "system", "content": "Answer ONLY using the provided context. Cite sources as [Doc N]."},
    {"role": "user", "content": f"Context:\n{context}\n\nQuestion: {query}"},
]
response = aoai.chat.completions.create(model="gpt-4o-mini", messages=messages, temperature=0)
print(response.choices[0].message.content)
Scenario: A legal team wants the assistant to answer questions using the company's constantly-updated internal policy documents (revised weekly), and every answer must cite the exact source paragraph.
Recommended answer: Implement RAG via a Foundry IQ Knowledge Base over an Azure AI Search index — not fine-tuning.
Rationale: Fine-tuning bakes facts into model weights at training time, making weekly updates impractical and it doesn't reliably produce verifiable citations. RAG retrieves the latest indexed documents at query time, so re-indexing (not retraining) propagates new policy text immediately, and the model can cite the exact retrieved chunk.

4. Prompt engineering & model parameters

Prompt components (Chat Completions roles)

  • system — sets persona, tone, rules, and constraints for the whole conversation (e.g., "You are a factual, concise support agent for Contoso").
  • user — the end-user's input/question.
  • assistant — prior model responses, also used to seed few-shot examples of desired output style.

Core techniques

  • Instructions — explicit, structured instructions (bulleted requirements) generally outperform a single vague sentence.
  • Few-shot prompting — include 2–5 example input/output pairs in the prompt to steer format/style without fine-tuning.
  • Primary content separation — clearly delimit instructions vs. the text to act on (e.g., triple quotes, XML-like tags) so the model doesn't confuse data with commands (also mitigates prompt injection).
  • Chain-of-thought style cues ("think step by step") help classic GPT chat models on reasoning-heavy tasks.
Reasoning models (gpt-5/o-series) are explicitly called out as not needing classic prompt-engineering tricks like elaborate few-shot examples or "think step by step" — over-engineering the prompt can actually hurt these models. Give them a clear goal and let internal reasoning do the work.

Key inference parameters

ParameterEffectGuidance
temperatureControls randomness (0–2 typical range, often 0–1 used)Lower (≈0) = deterministic/factual; higher = more creative/varied. Use low values for extraction, classification, code.
top_pNucleus sampling — restricts token choices to the smallest set whose cumulative probability ≥ top_pAlternative to temperature; Microsoft recommends changing one of temperature or top_p, not both.
max_tokens / max_completion_tokensCaps length of the generated outputAlso protects against runaway cost/latency; too low truncates answers mid-thought.
frequency_penaltyPenalizes tokens based on how often they've already appearedReduces repetition in long outputs.
presence_penaltyPenalizes tokens that have appeared at all, encouraging new topicsPush toward more diverse content.
stopSequence(s) that end generationUseful for structured/delimited outputs.
seedRequests (best-effort) reproducible outputCombine with low temperature for repeatable test scenarios.
nNumber of completions to generate per promptUseful for sampling/voting strategies; multiplies cost.
Must know: Adjust either temperature or top_p for a given call — never both at once — and use low temperature/top_p for deterministic, factual, or extraction-style tasks (this exact wording shows up as an exam distractor).

Worked example — tuning parameters for deterministic extraction

Python 
response = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[
        {"role": "system", "content": "Extract the invoice number, total, and due date as plain text."},
        {"role": "user", "content": invoice_text},
    ],
    temperature=0,        # deterministic — do NOT also set top_p
    max_tokens=100,
    frequency_penalty=0,
    presence_penalty=0,
    seed=42,              # best-effort reproducibility for regression tests
)
print(response.choices[0].message.content)

5. Function calling & structured outputs

Function (tool) calling

Function calling lets the model decide, based on the conversation, to invoke one of the functions/tools you declared in the request — the model never executes code itself; it returns a JSON object describing which function to call and with which arguments, and your application executes it.

  1. Send the Chat Completions request with a tools array (each with a name, description, and JSON Schema parameters) and tool_choice (e.g., "auto").
  2. If the model wants to call a tool, the response contains tool_calls with a function name and a JSON-encoded arguments string — your code parses it and calls your real function/API.
  3. Append a message with role: "tool", the tool_call_id, and the function's result, then call the Chat Completions API again so the model can produce the final natural-language answer.

Parallel function calling lets the model request multiple tool calls in a single response (e.g., "What's the time in Tokyo, Paris, and SF?" → 3 tool_calls in one turn).

Function calling via the newer Responses API uses a different request/response shape than Chat Completions — know that both APIs exist and that function calling is not identical across them.

Structured outputs

  • Structured outputs force the model to strictly conform to a JSON Schema you supply (via response_format in Chat Completions, or text.format in the Responses API).
  • This supersedes the older JSON mode, which only guaranteed syntactically valid JSON but not conformance to your specific schema.
  • In Python, commonly paired with Pydantic models passed via client.beta.chat.completions.parse(..., response_format=MyModel), returning a .parsed object.
  • Primary use cases: reliable function-calling argument generation, structured data extraction, and multi-step agentic workflows that need predictable shapes between steps.

Worked example — function/tool calling loop

Python 
import json
from openai import OpenAI
client = OpenAI(base_url="https://YOUR-RESOURCE-NAME.openai.azure.com/openai/v1/",
                 api_key=api_key)

tools = [{
    "type": "function",
    "function": {
        "name": "get_current_time",
        "description": "Get the current time in a given location",
        "parameters": {
            "type": "object",
            "properties": {"location": {"type": "string", "description": "The city name"}},
            "required": ["location"],
        },
    },
}]

messages = [{"role": "user", "content": "What's the current time in Tokyo?"}]

# 1) Ask the model; it may decide to call a tool
response = client.chat.completions.create(model="gpt-4o-mini", messages=messages,
                                            tools=tools, tool_choice="auto")
msg = response.choices[0].message
messages.append(msg)

# 2) Execute the tool call(s) your app owns, then feed results back
if msg.tool_calls:
    for call in msg.tool_calls:
        args = json.loads(call.function.arguments)
        result = get_current_time(args["location"])  # your real function
        messages.append({"tool_call_id": call.id, "role": "tool",
                          "name": call.function.name, "content": result})

# 3) Call again so the model can produce the final natural-language answer
final = client.chat.completions.create(model="gpt-4o-mini", messages=messages)
print(final.choices[0].message.content)

Worked example — JSON mode vs. structured outputs

Python (JSON mode) 
response = client.chat.completions.create(
    model="gpt-4o-mini",
    response_format={"type": "json_object"},  # guarantees *valid JSON*, not a specific shape
    messages=[
        {"role": "system", "content": "You are a helpful assistant designed to output JSON."},
        {"role": "user", "content": "Who won the World Series in 2020?"},
    ],
)
print(response.choices[0].message.content)
Python (Structured Outputs, strict schema) 
from pydantic import BaseModel

class InvoiceExtraction(BaseModel):
    invoice_number: str
    total_amount: float
    due_date: str

completion = client.beta.chat.completions.parse(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": invoice_text}],
    response_format=InvoiceExtraction,  # strict JSON Schema conformance guaranteed
)
invoice = completion.choices[0].message.parsed
print(invoice.invoice_number, invoice.total_amount, invoice.due_date)
Must know: Structured outputs guarantee schema conformance (strict JSON Schema match); JSON mode only guarantees valid JSON syntax. Also remember the 3-step function-calling loop: declare tools → model emits tool_calls → app runs the function and feeds the result back as a role: "tool" message for a final answer.

6. Evaluating models & apps (hallucination, relevance, quality, safety)

Foundry's Observability capability provides built-in evaluations and tracing for both raw models and full agent/app flows, viewable as dashboards in the Foundry portal.

Common evaluation dimensions

  • Groundedness / fabrication detection — does the answer stay faithful to the retrieved/provided source content, or does it hallucinate facts not present in context? Critical for RAG apps.
  • Relevance — does the response actually address the user's query/intent?
  • Coherence & fluency — is the output well-formed, logically structured language?
  • Similarity — how close is a generated answer to a reference/ground-truth answer (useful for regression testing prompts).
  • Safety metrics — violence, hate/unfairness, sexual, self-harm content, and protected-material/IP risk, scored similarly to content-filter categories but applied as an offline evaluation step.

Evaluations can run as AI-assisted (model-graded) metrics (another LLM scores the output against a rubric) or traditional NLP metrics (e.g., BLEU/ROUGE-style string overlap) — AI-assisted graders are generally preferred for nuanced qualities like groundedness.

Tracing captures the full chain of a request (retrieval calls, tool calls, intermediate model calls) so you can debug exactly where a hallucination or irrelevant answer was introduced — not just inspect the final output.
Must know: Groundedness is the specific evaluation metric name for hallucination/fabrication detection relative to supplied context — expect the exam to test that you can match "detecting fabricated/unsupported claims" to this term.

7. Content filtering & responsible AI guardrails

Azure OpenAI/Foundry Models include a built-in content filtering system powered by Azure AI Content Safety, which runs both the prompt and the completion through classification models to detect and block harmful content.

Filter categories (neural multi-class classifiers)

CategoryCovers
Hate and FairnessDiscriminatory language toward protected attributes: race, ethnicity, gender identity, sexual orientation, religion, disability, appearance, harassment/bullying
SexualSexual anatomy/acts, erotic content, abuse, child exploitation (zero-tolerance)
ViolencePhysical harm, weapons, extremism, stalking
Self-HarmSuicide, self-injury related language

Each category is scored across four severity levels: safe, low, medium, high. "Safe" is annotated but never filtered/blocked, and isn't configurable. You can configure thresholds for low/medium/high per category (within allowed limits for your subscription tier).

Additional optional classifiers

  • Jailbreak risk detection — flags attempts to bypass system instructions/safety guardrails (prompt injection style attacks).
  • Protected material (text & code) — detects verbatim reproduction of known copyrighted text or source code; using the protected material code model may be required for Customer Copyright Commitment coverage.

Important scope notes

  • Content filtering does not apply to embeddings models or audio models such as Whisper.
  • Prompts/completions are not stored for content-filter purposes and are not used to train/retrain the filtering models without consent.
  • Filtering can act on both the input prompt (blocking the call before it reaches the model) and the output completion (blocking/withholding a generated response).
  • Beyond content filtering, Azure OpenAI performs separate abuse monitoring to detect usage patterns that may violate product terms.
Governance: Foundry lets you apply Microsoft Entra identity, RBAC, content filters, and network isolation centrally as part of the "Foundry control plane," so filtering policy can be managed at the platform level, not just per API call.
Must know: There are exactly 4 default harm categories (Hate & Fairness, Sexual, Violence, Self-Harm), each with 4 severity levels (safe/low/medium/high), and content filtering does not cover embeddings or audio/Whisper models — a classic exam trap.
Scenario: A healthcare chatbot occasionally receives messages from distressed users mentioning self-harm. The compliance team wants the app to never hard-block these messages outright (so it can route to a crisis-support response) while still blocking genuinely violent or hateful content at default thresholds.
Recommended answer: Configure a custom content filter that raises the Self-Harm category severity threshold (e.g., allow medium severity through) while leaving Hate & Fairness/Violence/Sexual at default, and pair it with an application-level safe-response/escalation flow — not by disabling filtering entirely.
Rationale: Azure AI Content Safety lets you tune the block threshold per category (within subscription-allowed limits); you cannot disable the "safe" tier, but you can raise the bar for one category so legitimate but sensitive content reaches your app's custom handling logic instead of being blocked outright.

8. Fine-tuning

Fine-tuning (supervised fine-tuning, SFT, via Managed Training in Foundry) further trains a supported base model on your own labeled examples to change its behavior, tone, format-following, or domain specialization — it is not a substitute for RAG when you need the model to know new facts.

Data preparation

  • Separate training.jsonl and validation.jsonl files, one JSON object per line, each containing a messages array in the same system/user/assistant shape used by Chat Completions.
  • Keep a held-out test set separate from both training and validation data.
  • Specialized formats exist for vision fine-tuning and tool/function-calling fine-tuning.

Key hyperparameters

HyperparameterDescription
batch_sizeNumber of examples processed per forward/backward pass; larger batches = fewer, lower-variance updates
learning_rate_multiplierScales the learning rate; smaller values can reduce overfitting
n_epochsNumber of full passes over the training set; more epochs can improve fit but risks overfitting

Most hyperparameters can be left as auto for the service to choose sensible defaults.

Workflow

  1. Prepare/upload training + validation data.
  2. Choose a supported base model and training region, and a training type (e.g., SFT; some models also support preference-based tuning such as DPO at a conceptual level — aligning model outputs to preferred vs. rejected response pairs rather than single "correct" labels).
  3. Configure hyperparameters, start the job, and monitor training/validation loss.
  4. Once complete, deploy the fine-tuned model like any other model deployment (it gets its own deployment name) — commonly first evaluated using the Developer deployment type before a full production deployment type is chosen.
Required Foundry RBAC: Foundry User role is enough to run training; you need Foundry Owner to also deploy the resulting fine-tuned model.

Worked example — submitting a supervised fine-tuning job

Python (OpenAI SDK) 
import os
from openai import OpenAI

client = OpenAI(
    base_url=os.environ["AZURE_OPENAI_ENDPOINT"].rstrip("/") + "/openai/v1/",
    api_key=os.environ["AZURE_OPENAI_API_KEY"],
)

# 1) Upload training & validation files (JSONL, one chat-message example per line)
training_file = client.files.create(file=open("training.jsonl", "rb"), purpose="fine-tune")
validation_file = client.files.create(file=open("validation.jsonl", "rb"), purpose="fine-tune")

# 2) Create the SFT job
job = client.fine_tuning.jobs.create(
    training_file=training_file.id,
    validation_file=validation_file.id,
    model="gpt-4o-mini-2026-xx-xx",            # FINE_TUNING_MODEL
    method={
        "type": "supervised",
        "supervised": {"hyperparameters": {"batch_size": "auto",
                                            "learning_rate_multiplier": "auto",
                                            "n_epochs": "auto"}},
    },
    suffix="contoso-support-v1",
)
print(job.id, job.status)

Scenario: A support-ticket triage app needs responses that always follow a strict company tone-of-voice and always reply in a fixed 3-sentence structure. The facts needed are already supplied in each prompt by the retrieval layer; only output style and format are inconsistent.
Recommended answer: Use supervised fine-tuning (SFT) with example training.jsonl/validation.jsonl pairs demonstrating the desired tone/format — not RAG and not just prompt engineering alone.
Rationale: The problem is consistent behavior/format, which is exactly what fine-tuning optimizes for; RAG only helps inject facts, which aren't the issue here. Few-shot prompting could help but doesn't scale as reliably as fine-tuning once you need it to hold across thousands of varied tickets.
Must know: Fine-tuning data uses the same chat message schema (system/user/assistant) as normal Chat Completions calls, split into training.jsonl/validation.jsonl; fine-tuning changes style/behavior, while RAG supplies facts — don't conflate the two on the exam.

9. SDKs, authentication & connecting an app to a Foundry project

  • Endpoint shape: Foundry/Azure OpenAI resources expose an OpenAI-compatible endpoint, e.g. https://YOUR-RESOURCE-NAME.openai.azure.com/openai/v1/, usable directly with the official OpenAI Python/JS SDK (not only an Azure-specific SDK) by overriding base_url.
  • Authentication options:
    • API key — simplest, passed as api_key; less secure, avoid in production/shared code.
    • Microsoft Entra ID (Azure AD) — recommended for production; use DefaultAzureCredential + get_bearer_token_provider (scope https://ai.azure.com/.default) to mint a bearer token used as the API key. Requires a custom subdomain configured on the resource.
  • APIs available: Chat Completions API (classic, widely supported), the newer Responses API (different request/response shape, used for newest features like certain function-calling and computer-use flows), and the Assistants/Agent patterns for stateful, tool-using agents.
  • Connecting to a Foundry project: apps/agents reference a project's connections (model deployments, Azure AI Search, storage, etc.) so that swapping a backing resource doesn't require rewriting application code — this is the basis of Foundry Agent Service "hosted agents" and "prompt agents."
  • Foundry Toolbox: built-in tools, memory, and retrieval components you can attach to an agent without writing custom integration code.
Must know: You authenticate with either an API key or a Microsoft Entra ID bearer token; Entra ID is the Microsoft-recommended production approach and requires a custom subdomain on the Foundry/Azure OpenAI resource — a frequently tested prerequisite.

10. Quotas & rate limits (TPM / RPM)

  • Quota is expressed in Tokens-Per-Minute (TPM) allocated to a deployment; RPM (requests per minute) is derived automatically from the TPM setting.
  • Quota is scoped at the Azure subscription level, not the tenant level — it is the top-level boundary for how much capacity you can allocate across all your deployments.
  • As of mid-2026, Foundry introduced subscription-level shared quota pools: all Global Standard deployments of the same model + version across every region in a subscription draw from one shared pool; Data Zone Standard deployments share a pool per data zone (US/EU/APAC).
  • Quota tiers (Free, Tier 1–6) automatically increase available quota as usage grows, reducing manual quota-increase requests; tier assignment depends on usage history and commercial relationship (e.g., Enterprise Agreement). You can opt out of automatic tier upgrades.
  • Exceeding TPM/RPM limits returns an HTTP 429 (Too Many Requests) — applications should implement exponential backoff/retry.
  • Provisioned Throughput (PTU) deployments are not subject to the same shared-pool token throttling model — you reserve dedicated capacity instead, trading flexibility for guaranteed throughput/latency.
When designing for scale, remember quota is requested/managed per subscription and (for standard deployments) now pooled per model+version — deploying the same model across many regions doesn't multiply your quota automatically.
Must know: Quota is enforced at the subscription level (not per-resource, not per-tenant), is measured primarily via TPM, and throttled requests return HTTP 429 — expect the exam to test this scope level and the correct retry behavior.

Worked example — handling HTTP 429 with exponential backoff

Python 
import time
from openai import OpenAI, RateLimitError

client = OpenAI(base_url="https://YOUR-RESOURCE-NAME.openai.azure.com/openai/v1/", api_key=api_key)

def call_with_backoff(messages, max_retries=5):
    for attempt in range(max_retries):
        try:
            return client.chat.completions.create(model="gpt-4o-mini", messages=messages)
        except RateLimitError:
            wait = 2 ** attempt  # exponential backoff: 1,2,4,8,16s
            print(f"429 received, retrying in {wait}s...")
            time.sleep(wait)
    raise RuntimeError("Exceeded max retries after repeated 429 responses")
Scenario: You deployed the same gpt-4o-mini model as Global Standard in three regions to "multiply" available throughput for a high-traffic app, but you're still hitting 429s at roughly the same aggregate volume as a single-region deployment.
Recommended answer: This is expected — quota for Global Standard deployments of the same model+version is pooled at the subscription level, not per region, so deploying across regions does not add capacity; request a quota increase or move the workload to PTU.
Rationale: Since mid-2026, Foundry pools Global Standard quota per model/version across all regions in a subscription. Spreading identical deployments across regions improves resilience/latency locality, not total throughput — a key distinction the exam tests.

Pattern A: RAG retrieval + chat completion + citation formatting

Python 
from azure.search.documents import SearchClient
from azure.core.credentials import AzureKeyCredential
from openai import AzureOpenAI

search_client = SearchClient("https://my-search.search.windows.net", "kb-index",
                              AzureKeyCredential("<search-key>"))
aoai = AzureOpenAI(azure_endpoint="https://my-resource.openai.azure.com/",
                    api_key="<key>", api_version="2026-xx-xx")

def answer_with_citations(question: str) -> str:
    hits = list(search_client.search(search_text=question, top=4,
                                       query_type="semantic", semantic_configuration_name="default"))
    sources = "\n\n".join(f"[{i+1}] ({h['title']}) {h['content']}" for i, h in enumerate(hits))

    messages = [
        {"role": "system", "content": (
            "Answer using ONLY the numbered sources below. Every factual claim must end "
            "with a bracketed citation like [1]. If the sources don't contain the answer, say so.")},
        {"role": "user", "content": f"Sources:\n{sources}\n\nQuestion: {question}"},
    ]
    resp = aoai.chat.completions.create(model="gpt-4o-mini", messages=messages, temperature=0)
    return resp.choices[0].message.content

print(answer_with_citations("What is our data-retention policy for support tickets?"))

import json

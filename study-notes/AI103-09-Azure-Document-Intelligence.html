1. What Azure AI Document Intelligence Does

Azure AI Document Intelligence (in Azure AI Foundry Tools) is a cloud-based service that uses machine learning and OCR to automate extraction of text, structure, and key data from forms and documents — invoices, receipts, IDs, contracts, tax forms, mortgage applications, and general unstructured content. It turns scanned/digital documents into structured, business-ready JSON output that applications can consume directly.

It sits within the broader Azure AI Content Understanding family: Document Intelligence provides high-accuracy, deterministic extraction from structured documents, while Content Understanding also offers LLM-powered analyzers for complex, unstructured, multimodal content. Together they prepare grounded data for intelligent agents and RAG apps.

Three model families

  • Document analysis models — Read (OCR) and Layout: general-purpose extraction with no predefined schema.
  • Prebuilt models — Microsoft-trained models with fixed schemas for common document types (invoice, receipt, ID, W-2, etc.). No training required.
  • Custom models — Train on your own labeled documents to extract fields specific to your business; can be composed together.
Version note: v4.0 (2024-11-30) is the current GA API. v3.0 and v2.1 are retiring (v3.0 ends March 2029, v2.1 ends Sept 2027) — v4.0 merged the old "General document" key-value-pair model's functionality into the Layout model.
Must know: Document Intelligence = deterministic, schema-driven extraction (OCR + layout + fields). If the exam scenario needs grounded, structured JSON from known document types, this is the answer — not a generic LLM call.

2. Read Model (OCR) — The Foundation

The Read model is the core OCR engine. It extracts printed and handwritten text from PDFs, images, and Office files (Word, Excel, PowerPoint, HTML). It detects paragraphs, text lines, words, their locations (bounding boxes), and detected languages.

Critical relationship: Read is the underlying engine used by Layout, prebuilt models (Invoice, Receipt, ID, Health Insurance Card, W-2, etc.), and custom models. You rarely call Read in isolation unless you just need raw text (e.g., digitizing documents, compliance archiving, pre-processing handwritten notes before translation).

Key capabilities

  • Model ID: prebuilt-read
  • Higher resolution than Azure AI Vision Read OCR — optimized for dense/large text-heavy documents rather than real-time photo scenarios (use Vision Image Analysis Read for signs/labels/real-time UX).
  • Supports searchable PDF output — converts a scanned-image PDF into a PDF with embedded, searchable text (specify output=pdf on the analyze call). Only prebuilt-read supports this, at no extra cost.
  • Detects languages, paragraph boundaries, and (via add-ons) formulas, barcodes, and font styles.
Read supports more file types than you'd expect: PDF, JPEG/PNG/BMP/TIFF/HEIF images, and DOCX/XLSX/PPTX/HTML office documents in v4.0.
Must know: Read is the shared OCR foundation — every other model (Layout, prebuilt, custom) builds on it. If asked "what extracts handwritten + printed text as the base layer," the answer is Read, model ID prebuilt-read.

3. Layout Model

The Layout model (prebuilt-layout) extracts text, tables, selection marks, and document structure without needing a predefined schema. It combines OCR with deep-learning structure analysis to identify both:

  • Geometric roles — text, tables, figures, selection marks (checkboxes).
  • Logical roles — titles, section headings, page headers/footers, page numbers, footnotes.

Data extracted

Note: the legacy "General document" model (key-value pair extraction without training) has been folded into the Layout model's capabilities in v4.0 via the keyValuePairs add-on feature.

Use Layout when you need structure (tables, headings, checkboxes) from a document whose format varies or isn't covered by a prebuilt model — e.g., ingesting arbitrary PDFs/reports into a knowledge base.
Must know: Layout = structure extraction (tables, selection marks, paragraph roles) with no training needed. It is the model exam questions point to for "extract tables/structure from generic documents" and for producing Markdown output for RAG ingestion.

Prebuilt models let you add intelligent document processing without training — Microsoft defines and maintains the field schema (e.g., InvoiceDate returned as type date, SubTotal as type currency), so normalization is automatic.

5. Custom Models

Custom models are trained on your own labeled datasets to extract fields specific to your business that aren't covered by a prebuilt schema. You label as few as 5 example documents of the same type to get started.

Custom extraction model types

TypeBest forNotes
Custom template (custom form)Static, consistent visual layouts (structured forms, questionnaires)Supports key-value pairs, selection marks, tables, signature fields, regions; any supported language; max 500 training pages, 50 MB training data
Custom neural (custom document)Mixed-type / structured, semi-structured, and unstructured documentsDeep-learning base model fine-tuned on your data; supports overlapping fields, signature detection, table/row/cell confidence; max 50,000 training pages, 1 GB training data; generally higher accuracy — recommended default when supported
Custom composedCombining multiple standalone custom extraction models under a single model IDSubmit one document, service matches it to the right component model

Custom classification model

Identifies the document type/class before an extraction model runs — useful when incoming documents are a mixed bag (e.g., a scanned mailroom batch) and you need to route each to the correct extraction model. Supported since API 2023-07-31. Max training data: 1–2 GB, up to 10,000 pages.

Decision rule: Prebuilt if the doc type matches a Microsoft schema (invoice, receipt, ID, tax form) → fastest, no training. Custom template if your forms are static/consistent and prebuilt doesn't fit. Custom neural if layouts vary or documents are semi-/unstructured. Classifier + composed model if you receive multiple document types in one pipeline.
Must know: Custom neural models are recommended over custom template models for higher accuracy whenever both are supported for your language — template models are template/layout-sensitive; neural models generalize better across layout variance.

6. Output Formats & RAG/Agent Integration

All analysis operations return structured JSON (analyzeResults) containing pages, paragraphs, tables, key-value pairs, selection marks, and (for prebuilt/custom) typed fields. This structured, grounded output is what distinguishes Document Intelligence from a free-form LLM summarization approach.

Key output features for downstream AI pipelines

  • Markdown output (Layout model) — renders extracted content (headings, tables, paragraphs) as Markdown text, which is far easier for an LLM/agent to reason over than raw JSON geometry. This is the natural bridge into a RAG (retrieval-augmented generation) pipeline.
  • Searchable PDF (Read model) — embeds extracted text into the original PDF for full-text search without altering the visual document.
  • Query fields / keyValuePairs add-ons — let you request specific fields dynamically (query fields) or general key-value extraction, even outside a trained schema.
  • Typed field values — string, number, integer, date, time, phoneNumber, currency, address — auto-normalized so downstream code doesn't need to parse raw strings.

Typical RAG / grounding pattern (exam-relevant)

  1. Ingest documents (PDFs, scans, Office files) → analyze with Layout or a prebuilt/custom model.
  2. Take the Markdown/JSON output → chunk it → generate embeddings.
  3. Index chunks in Azure AI Search (vector + keyword/hybrid index).
  4. At query time, retrieve relevant chunks and ground an LLM/agent response (Azure OpenAI / Azure AI Foundry Agent Service) in the extracted, verifiable document content — reducing hallucination versus asking the LLM to read raw scanned images itself.
Document Intelligence doesn't do retrieval or embeddings itself — it only extracts/structures content. Pair it with Azure AI Search for indexing/retrieval and Azure OpenAI/Foundry Agents for generation — this combination is the classic AI-103 "information extraction → RAG" exam pattern.
Must know: When a scenario needs document content fed into an LLM/agent or search index with high fidelity and traceability, the pipeline is Document Intelligence (extract) → chunk/embed → Azure AI Search (index/retrieve) → Azure OpenAI/Agent (generate). Markdown output from the Layout model is the preferred bridge format.

7. Resources, Pricing Tiers & Service Limits

Resource & pricing tiers

  • F0 (Free tier) — limited: only first 2 pages of a PDF/TIFF processed; 4 MB max file size.
  • S0 (Standard/paid tier) — full processing; 500 MB max file size; up to 2,000 pages per PDF/TIFF.
  • Created as a Document Intelligence (Cognitive Services / Foundry) resource in the Azure portal; get key + endpoint to call REST API or SDKs (C#, Python, Java, JavaScript).
  • Development/testing can be done visually via Document Intelligence Studio (no-code UI for trying models, labeling custom training data, and viewing full JSON output).

Version retirement to remember: v3.0 retires March 30, 2029; v2.1 retires Sept 15, 2027. v4.0 and v3.1 have no announced end-of-support date. Always migrate forward before a retirement date.
Must know: Free tier (F0) only processes the first 2 pages of multi-page docs and caps file size at 4 MB — a classic distractor in exam questions about "why isn't my whole document being analyzed."

8. Exam Quick Reference

If the scenario says…Use…
Just need raw printed/handwritten text, or a searchable PDFRead model (prebuilt-read)
Need tables, checkboxes, headings/structure from varied/unknown-format documentsLayout model (prebuilt-layout)
Document type is invoice, receipt, ID, W-2, mortgage form, etc.Matching prebuilt model — no training needed
Business-specific fields on consistent/static formsCustom template model
Business-specific fields on varied/semi-structured/unstructured documentsCustom neural model (preferred for accuracy)
Mixed batch of multiple document types arriving togetherCustom classifier + composed model
Need to feed extracted content into an LLM/agent or search index for RAGLayout's Markdown output → Azure AI Search index → Azure OpenAI/Agent generation
Field values need to come back already typed (dates, currency, addresses)Prebuilt models (auto-typed) or custom models (you define the type per field)
Top trap to avoid: Don't confuse Document Intelligence (deterministic schema-based extraction) with Azure AI Content Understanding's LLM-powered analyzers (for complex/multimodal unstructured content) — the exam may ask you to pick the "right AI tool" between the two.
